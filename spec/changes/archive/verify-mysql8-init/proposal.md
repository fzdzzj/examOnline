# 提案：MySQL 8 空库初始化与存量迁移真机验证（前后端优化组合·提案⑥，P2）

## Why

`fix-schema-mysql-pk`（阶段 17）为 `schema.sql` 全部自增表补了 `PRIMARY KEY (id)`，但**证据止于文本约定测试 + H2 全量绿**（遗留 #9）：从未在真实空 MySQL 8 实例上执行过 `schema.sql`，`2026-W16-add-primary-keys.sql` 存量迁移也从未在真实存量库上跑过。`schema.sql` 是 H2/MySQL 双兼容的唯一建表入口（AGENTS.md 硬约定 1），这条真机验证是它的最终闭环——验证通过前，不得声称「MySQL 8 新环境可启动」已端到端验证。

**前置**：无业务前置；需要可用的 MySQL 8 实例（`docker/mysql` 既有编排可复用）。属后端独立立项（验证类），不塞进前端阶段 19–23 串行链。

## What Changes

1. **空库真机初始化**：起真实空 MySQL 8 实例，执行 `schema.sql`，验证全部业务表建成、无报错，记录原始输出；
2. **存量迁移真跑**：按迁移前形态构造存量库（缺主键的旧表结构），执行 `2026-W16-add-primary-keys.sql`，验证补主键成功；再重复执行一次，确认「主键已存在的失败可忽略且不改业务数据」与脚本头注声明一致；
3. 验证记录（实际执行的命令 + 该次原始输出 + 当时短 revision）入 `docs/**` 作为证据；
4. 若真跑暴露缺陷：修 `schema.sql`（唯一建表入口）或迁移脚本属本变更收口的一部分，并同步既有约定测试——**不得「验证失败但登记完成」**；
5. 结果登记回遗留清单（收口 #9，或如实记录失败原因）。

## Impact

### 受影响的规范
- `spec/specs/data-access/spec.md` — MODIFIED：新库建表可在 MySQL 8 执行、AUTO_INCREMENT 列必须有主键（各补真机执行场景）。

### 受影响的文件
- `src/main/resources/schema.sql`（仅当真跑暴露缺陷时修）
- `docker/mysql/migrations/**`（同前）
- `docs/**` 验证记录
- `src/test/**`（仅当需同步既有约定测试时）

### 需要迁移
- [ ] 数据库迁移（无新增；本变更恰是给既有迁移补真跑证据）

## 时间线评估

小–中：约 1 天（环境与执行 0.5–1 天；若暴露缺陷，修复另计）。

## 风险

- 真 MySQL 8 与 H2 的方言差异可能到真跑才暴露——这正是本变更的目的，属预期内发现，不算意外；
- **迁移脚本没有自动执行者是既有硬约定**（AGENTS.md 约定 4）：真跑由人按序执行并验证，不造自动执行机制，「脚本已提交」永远不等于「迁移已生效」；
- 存量库必须按迁移前形态构造（缺主键旧表），不是拿新库直接跑迁移——否则测的是空转；
- 修复 `schema.sql` 时保持 H2/MySQL 双兼容与 `AUTO_INCREMENT + PRIMARY KEY (id)` 同块约定。

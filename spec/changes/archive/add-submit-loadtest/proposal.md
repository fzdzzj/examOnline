# 提案：交卷链路 5000 并发压测（前后端优化组合·提案⑤，P2）

## Why

交卷链路的三重幂等、MQ 削峰、显式消费并发与容量模型都已合入，但 **5000 并发压测从未执行**（遗留 #1：仓库内无任何 `.jmx` 或压测报告）。`add-mq-trace-and-capacity`（阶段 10）只提供可复算的容量模型，收尾时明确「具体数值仍须真跑压测定稿，该变更不替代实测」——`spec/specs/exam-taking/spec.md` 的「交卷落库容量与时延」Requirement 目前只有参数生效与容量估算场景，**没有任何真跑证据**。方向 D 的纪律：实测先行，无证据不优化。

**前置**：建议排在提案①②之后（压测口径含前端联调后的完整负载模型）；真跑需要可用的 dev 实例（MySQL + RabbitMQ + Redis）。属后端独立立项（验证类），不塞进前端阶段 19–23 串行链。

## What Changes

1. 新增 JMeter 压测资产：`.jmx` 场景脚本 + 5000 学生/考试数据构造脚本 + 执行说明，全部入仓库可复现；
2. 在真 dev 实例上执行 5000 并发交卷压测，采集硬指标：**提交 P99 < 2s、0 丢单、批量落库完成 < 30s**；
3. 以真跑数据校准容量模型（吞吐 ≈ 并发 × 单批大小 / 单批耗时），调参结论包含与数据库连接池上限的联动约束；
4. 压测报告入 `docs/**`（实际执行的命令 + 该次原始输出 + 当时短 revision 三要素），作为「交卷落库容量与时延」Requirement 的实测证据；
5. 不改后端实现：若压测暴露必须改代码的瓶颈，停下回报另立项（提案⑪即为此预置的候选，门控于本提案）。

## 时间线评估

中：约 2–3 天（资产与数据构造 1 天 + 真环境执行与调参 1–1.5 天 + 报告 0.5 天）。

## 风险

- **硬指标以真跑为准**：不达标时先调容量参数（消费并发/批量/连接池）并复跑；不得为凑指标改指标定义、改测试或只报最好的一轮；
- 压测数据构造必须可复现（脚本随资产入库，任何人可重建同场景）；
- 不顺手改生产配置默认值——调参结论记录在报告里，改默认值须另行决策；
- 压测期间同轮采集队列深度、消费 lag 等中间件指标，报告里给出与既有告警阈值的关系；
- 门禁与压测互不替代：后端 surefire 回归照跑，压测报告不进 CI 门禁。

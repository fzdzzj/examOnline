# 提案：把压测机和被测应用分开（isolate-submit-load-generator）

> 状态：已收口（2026-09-28）。阶段 1 已实施入库，凭据是 `loadtest/tests/guards.sh` 实跑退出码 0（命令、当次输出与 revision 见同目录 `tasks.json` 阶段 1 的 evidence 字段）；阶段 2 判**不可执行**——无第二台物理宿主，本地 Docker 不构成独立宿主，同机采样不得写成已分离；阶段 3 按「阶段 2 未做」收口。不改应用参数，不改交卷代码。将来若真有第二台物理宿主，**另立新变更**，不重启本目录。

## Why

`docs/submit-capacity-tuning-report.md` 已经把应用侧容量杠杆用完：线程上限单独调高是负优化；线程与连接池一起打开后，P99 仍不达标。当时应用进程只占约一个核的一小部分，整机 CPU 打满，MySQL 在库内排队。报告把「JMeter 与被测机同机」标成授权内、尚未做的下一步。

继续改 Tomcat、连接池、审计异步化或拆服务，没有新的测量支持。

**当前状态**：`loadtest/` 在同一台机器上启动 JMeter 和被测进程。

**期望状态**：压测结论能区分「应用慢」和「压测机把 CPU/IO 抢走」。分离之后仍用原指标，不改 P99 定义。

## What Changes

- 给 `loadtest/` 增加一种「压测进程不与被测进程同机」的跑法，并写明如何确认两边不在同一台宿主。
- 分离后按既有方法学复验一臂（至少三轮中位数、预热、轮间排空）。不调线程、不调池、不改业务代码。
- 若 P99 仍不达标，只登记下一个瓶颈位（仍可能是 MySQL 排队）。不得据此放宽指标，也不得顺手合并交卷 SQL。

## 时间线评估

小到中。取决于是否已有第二台机器或独立容器宿主。没有第二台机器时，本提案停在「跑法写明但未复验」，不得把同机结果改写成已分离。

## 风险

- 分离后 P99 仍不达标。缓解：如实登记，不改指标，不把未授权的 SQL 合并塞进本提案。
- 共享 dev 被压测写脏。缓解：只用既有 `loadtest/` 命名空间和复位脚本，并带 `--default-character-set=utf8mb4`。

# 提案：交卷链路容量调整与压测复验（tune-submit-capacity，P2）

## Why

`add-submit-loadtest`（提案⑤，已归档）四轮真跑判定：0 丢单与批量落库 < 30s 达标，**提交 P99 2088–3700ms 未达标**（目标 < 2s），根因定位为 Tomcat 线程上限（Spring Boot 默认 200 未配置，容量 ≈455 req/s < 场景需求 ≈490 req/s），JIT 预热归因被 A-B-A 对照证伪。该变更按任务边界把后续处置登记为判据 **G1/G2/G4/G5**（`docs/submit-loadtest-report.md` §8.3），本提案即这四条判据的执行立项——遗留 #1「交卷链路压测 P99 未达标」的收口载体。

**前置**：`add-submit-observability`（G3 观测补齐）**先行或同批**——报告明言「否则改动后仍无法证明有效」；若 G3 未落地，本提案的达标判定只能退回 JMeter 客户端侧口径（弱证据），须在报告里如实降级表述。

**属后端独立立项**（改并发运行参数），不在前端阶段 19–23 串行链内；与该链「一律不改后端」的纪律不冲突，但须在回报里写明这一点。

## What Changes

1. **G1 方案裁决**：量化「接受服务端均值 < 400ms 语义」vs「提高线程上限」两方案的代价（§4.2：`200/服务时长 > 500 req/s`），选定其一并把裁决依据入报告——不接受没有数字的「拍脑袋调参」；
2. **G2 线程上限注入**：`SERVER_TOMCAT_THREADS_MAX` 经 Spring Boot relaxed binding 由环境变量注入（可零文件改动）；若需在 dev 编排/压测脚本里固化，改 `docker-compose.yml` 或 `loadtest/**` 的注入点，并给出改后的**容量估算与新的瓶颈位**（下一个饱和点大概率是 MySQL 写入或宿主 CPU——本机 20 逻辑核为共享资源）；
3. **G4 压测方法学修订**：每臂 ≥3 轮取中位数、每轮前预热、轮间等 TIME_WAIT 排空（改 `loadtest/` 脚本，复用既有 `compare-runs.py` 多轮比对）；
4. **G5 Hikari 持续采样**：压测期间持续采样 Hikari `pending/active` 峰值（本报告此前只有突发后快照，属弱证据）；
5. **复验**：用修订后的方法学对调整后配置复跑压测，按硬指标判定（P99 < 2s / 0 丢单 / 批量落库 < 30s），**指标定义不得修改**（不达标就如实写不达标并给下一步瓶颈位，不硬凑）；
6. 报告更新（既有 `docs/submit-loadtest-report.md` 追加轮次或新开报告，三要素齐全）。

## Impact

### 受影响的规范
- `spec/specs/performance/spec.md` — ADDED：交卷容量可由运行参数调整且达标判定可复现（含「方法学不修订不得把冷启动当容量」场景）。

### 受影响的文件
- `loadtest/**`（方法学与采样脚本）
- `docker-compose.yml` 或 `loadtest/**` 里的环境变量注入点（仅当选定 G2 路线）
- `docs/**` 压测报告
- `src/main/**`、`src/test/**`、`pom.xml` 预期零改动（relaxed binding 注入不需改代码；若真发现必须改代码的瓶颈，停下回报另立项）

### 需要迁移
- [ ] 数据库迁移（无）

## 时间线评估

中：约 1–2 天（裁决与注入 0.5 天；三轮复跑与分析 1 天起，视环境可用性）。

## 风险

- 提高线程上限后瓶颈转移（MySQL 写入 / 宿主 CPU）——这正是 G2 要求给出新瓶颈位的原因，转移不等于失败，如实登记即可；
- 共享 20 逻辑核的宿主上三轮方差可能仍大——方法学修订（预热 + 中位数）就是为压制它，不得以方差为由回退到单轮口径；
- **压测期间 dev 栈为共享资源**：复跑须错开其它真实环境任务（MySQL/RabbitMQ/Redis 端口与容器名冲突，见工程惯例）。

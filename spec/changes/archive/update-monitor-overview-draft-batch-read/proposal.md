# 提案：监考总览按进行中学生批读草稿

> 状态：待审批（2026-09-26）。本提案只授权先归因；实现与规范合入取决于 GO/NO-GO 裁决。不可把上一变更的原始 MGET 耗时直接当作批读收益。

## Why

`MonitorService.overview` 已在权限和考试归属校验后取整场答卷；在线状态为一次 MGET、异常为聚合 SQL，但每份**进行中**答卷仍在 `buildStudentItem` 中调用 `ExamDraftService.get`，形成逐人 Redis GET + JSON 解析。`ExamDraftService.get` 同时用于自动保存冲突判断、断线恢复、交卷兜底与对账，不能为了监考性能改变这些路径的读写语义。

已归档的 `update-monitor-overview-submission-projection` 在隔离 H2 + Redis db15、200 人/120 进行中负载下，三轮独立组件臂的逐人草稿 GET+解析 passMedian 为 30.917/33.395/42.190ms；端到端并发 1 mean 为 30.42/31.88/32.96ms。组件臂与端到端**不是同一请求内计时，不能把两者相除当精确份额**。同轮原始 `multiGet` 只量取字符串，没有计入 JSON 解析、映射、缺键与损坏值处理，故不能据此宣称批读的端到端加速。旧 JSON、工具 revision 与限制见该归档目录；Redis db15 只隔离键空间，不保证宿主 CPU/网络隔离。

本提案的可检验假设是：在保持草稿解析和请求语义的前提下，监考总览可将进行中学生的逐人 Redis 往返改为一次批读，且同负载端到端收益超过轮间波动。最强反例是解析/序列化或 Redis/线程争用主导、批读响应过大增加峰值堆，或损坏/缺键/故障语义无法等价。反例成立即 NO-GO，不为追求调用数改变业务语义。

## What Changes

1. 先核对 `MonitorService`、`ExamDraftService.get` 与 `AntiCheatIntegrationTest`；在专用隔离环境用同一份可复现样本，**独立**测量逐人 `get`（含解析）、原始 MGET 与完整“批取＋逐值解析＋按学生关联”，以及真实旧总览的延迟分位/吞吐、Redis 命令次数、CPU/GC/堆、响应体。至少三轮，记录 revision、命令、原始输出和干扰；不把不同臂墙钟与 JFR CPU 份额相加或等值比较。样本覆盖旧测量的代表性负载，并有零人/单人、缺键/损坏草稿等正确性样本。不得写共享 dev、启 Docker 或使用未经授权的跨宿主压测。
2. 先判 GO/NO-GO：只有完整批取解析臂保持旧 `get` 语义，旧路径确属主要可控成本，且**预计请求级**收益高于同轮波动、内存/响应代价可接受时才 GO。不能隔离测量、只有原始 MGET 数字、收益不明或故障语义无法保持时 NO-GO，停止业务实现。
3. GO 后只在监考总览读路径按进行中学生的键批量获取草稿；无进行中答卷不查 Redis；成功路径不再逐人 GET。使单份 `get` 与批读共用或等价执行同一解析规则：缺键/空白/损坏返回无草稿，非对象答案按零题，损坏保留按学生定位的 ERROR 日志；Redis 调用异常仍向上抛，不把整批读取失败伪装成全员零进度。批读结果为空、长度与请求键不一致等异常结果不得静默对齐；学生 ID 与值要按位置或等价的可靠映射关联。仅改变监考总览读取方式，不改键格式/TTL/保存版本冲突、交卷/对账单份读、在线 MGET、SQL、权限或 API。
4. 先红后绿的确定性护栏核对旧实现的逐人 GET，守住进度、人数、异常高亮/排序、归属和错误边界；用相同数据、工具、预热与并发多轮复测**实施后的端到端**和组件臂，若收益不可辨、内存回归或语义破坏则回退实现并以 NO-GO 收口。只有 GO 且实现、复测、仓库根 `mvnw.cmd clean test` 均通过才合入下面的 delta；否则 delta 按未采用草案归档。

## Impact

- **规范**：仅条件性 MODIFIED `spec/specs/anti-cheat/spec.md` 的「监考大屏」Requirement，原实时状态与异常详情场景原样保留。`spec/specs/performance/spec.md` 已有先归因/一次只改一类门禁，不再新增同义条款。
- **代码（仅 GO）**：预计 `MonitorService` 和 `ExamDraftService` 的监考只读批取接口/共享解析；测试侧针对性护栏及隔离测量工具。其他调用 `ExamDraftService.get` 的自动保存、断线恢复、交卷和扫尾不改其调用或行为。
- **用户/API**：不改接口、返回字段、权限、在线/离线/已交卷计数、异常排序、进度近似口径；一次轮询的批量快照与旧逐人依次读取在并发保存时观察时点可能不同，这属于待验证的实时性边界，不能声称严格同一时刻等价。
- **部署/数据**：不改 schema、迁移、Redis 键协议与 TTL、JVM、线程池、缓存或前端；确认现有 Redis 部署及 MGET 支持后方可实现，不能根据单机 db15 结果外推生产 P99。

## 验收与停止条件

- 归因与复测须保留逐轮机器可读原始证据及校验清单，写清基线与实现 revision、JDK/负载/命令/退出码、mean/p50/p95/p99/吞吐、Redis 调用次数与完整解析时间、CPU/GC/堆及响应大小。并列呈现每轮，不挑最好的一轮；目标效果须超过轮间波动，不用硬编码的毫秒阈值替代判断。
- 测试覆盖无进行中学生、缺键/空白/损坏值、非对象 answers、错位/重复 ID、混合状态、批量读取异常和缺失/长度异常、归属拒绝；不能把损坏草稿当已答，也不能把 Redis 失败默默改成零进度。旧红须由预期逐人读取边界触发，而非桩/环境失败。
- 仅在已提交的 GO 实现 revision 上于仓库根执行唯一全量门禁 `mvnw.cmd clean test`（或 `./mvnw clean test`），证据写明当次四计数、BUILD、退出码、revision 与 AGENTS.md 自查。NO-GO 时实施/复测步骤保持未完成并注“不适用”，不能伪造通过；如提交了测量工具，也须对其提交态跑全量门禁并如实标明不是实现验收。

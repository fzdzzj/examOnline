# 提案：成绩排名计算先归因、再等价提速

> 状态：待审批；静态证据基于 2026-09-26 的 `31b70c3`。本提案不声称排名已是请求延迟的主要瓶颈。执行前必须重新核对 HEAD、工作树和现行规范。

## Why

`src/main/java/com/exam/score/service/RankCalculator.java:24-41` 对每份非空成绩逐一与全班分数比较，全部有效时有 `n × (n − 1)` 次候选比较，复杂度 O(n²)。当前三个调用者是发布预览（`ScoreService.java:234`）、学生查本人（`:308`）和导出排名（`ScoreExportService.java:394`）。学生查本人还会取回全班已汇总答卷（`ScoreService.java:293-309`），这是**另一类数据库取数工作**。

**已证实**的是代码结构和调用点；**未知**的是典型考试人数、各接口实际负载、数据库取数与 Java 排名各占多少时延、CPU/GC 及吞吐。`docs/submit-capacity-tuning-report.md` 针对交卷且压测机与被测进程同宿主，不能作为成绩查询的归因。`spec/specs/performance/spec.md` 已要求同负载先量延迟、吞吐、资源并一次只改占比最高的一类；不得用 O(n²) 推论直接取代测量。候选线索见 `docs/backend-optimization-candidates.md`。

**当前状态**：`RankCalculator.rank` 二重遍历；现有 `RankCalculatorTest` 守住常见并列、空值、空列表，但未验证数值相等而 scale 不同及计算增长；没有成绩查询路径的可归因测量。

**期望状态**：先在隔离、可复现的同一负载下分账请求总耗时、数据库取数、排名计算、CPU/GC 与吞吐。若证实排名计算是该路径占比最高的可控因素，再**只**替换纯函数的 O(n²) 比较结构，并在相同数据与负载下证明口径不变且改善可测。若数据库或其他因素占主导、测量环境不可用或改后无收益，停在如实评估，不实施/不宣称排名优化成功。

## What Changes

1. 对发布预览、学生查本人及导出调用关系复核，准备固定人数和分数分布的隔离样本；先量同负载下各路径请求延迟、吞吐、SQL 取数耗时、排名计算耗时和 CPU/GC，附命令、原始输出、机器/运行配置及 revision。不得以单次微基准冒充请求级归因，也不得写共享 dev 成绩。
2. 只有归因支持时，在 `RankCalculator` 的纯计算层做一次等价替换（目标比较增长不超过 O(n log n)），保持结果与输入顺序对应、`BigDecimal.compareTo` 数值并列、`null` 不参与且名次记 0、后续名次跳空。设计测试侧可计数比较的确定性护栏，让旧二重遍历先红、新实现后绿；不以墙钟超时作为单测判据。
3. 重新以**同一数据和负载**量接口与计算指标，单独报告计算层与端到端变化；跑已提交实现 revision 上的后端唯一门禁。无益或语义变化则回退代码并记录原因，不顺手改学生查分的全班 SQL、索引、缓存、JVM 或线程池。
4. 有实测效果且语义/门禁通过才合入 score-management delta、回勾/归档；否则按评估结论记录未采用与证据，不把拟实施条款合入规范基线。

## 风险与停止条件

- **误归因**：学生接口取回全班答卷，SQL 可能比排名计算更慢；隔离记录 SQL 与计算耗时，非计算主因则停止本代码优化，数据库取数另立提案。
- **语义退化**：排序重写可能因 `BigDecimal.equals` 与 `compareTo` 差别而拆散并列，或打乱输入位置/空值。用确定性边界 + 旧实现作为测试侧参考、不同 scale 与重复分数数据对照；保留本人不在榜单时的错误语义和复核隐藏。
- **微基准假收益**：JIT 预热、GC、样本分布、数据库并发不一致会误导；固定数据/环境、预热、逐次原始结果与 revision，报告计算指标与端到端指标，不能只比较算法循环耗时。
- **范围蔓延**：一次不改 SQL、缓存、JVM、线程池或其他候选；本变更不能冒充交卷 P99 修复。不得擅自跑共享 dev 写入、Docker 或跨宿主压测；没有隔离环境就停。

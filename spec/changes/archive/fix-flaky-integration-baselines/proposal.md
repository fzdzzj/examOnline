# 提案：收口偶发集成测试（fix-flaky-integration-baselines）

> 状态：已归档（2026-09-26）。验收边界=定向红绿（ed06f42 隔离工作树红灯 1/1/0/0——assertSame 见两个不同 AtomicLong，共享计数实现绿灯 1/0/0/0，命令、失败断言与 revision 见 tasks.json 证据字段）+ 已提交实现 revision d1dfcb6 全量门禁（mvnw.cmd clean test → 305/0/0/1，BUILD SUCCESS，退出码 0）；两条历史偶发各 3 次逐次复核未复现（41f8298），遗留 #14/#15 保持开放——归档只声称护栏已修与观察方法收口，不声称历史偶发已消除。

## Why

`spec/README.md` 遗留 #14、#15 仍开放：`DataRetentionIntegrationTest.purgeRemovesOnlyTerminalOldExams` 曾出现期望行数与实际不符，单类重跑又绿；`ExamTakingIntegrationTest.enterGateAndCountdown` 曾在教师注册步骤得到非预期状态。两次都没有稳定复现步骤，也没有改产品代码。

把「再跑一次就绿」当成基线，会让后面的优化分不清是产品回归还是测试抖动。

另有已证实的护栏缺口：`8bd04c2` 已把 `IntegrationTestBase` 的取号器改为跨实例共享的静态计数器，并在旧实现上观察到 `UniqueSeqGuardTest` 红、新实现绿；但现有测试靠紧凑创建 1000 个实例来碰同毫秒桶。1000 个实例落入 100000 个可能毫秒桶并不构成无条件的鸽笼保证；执行变慢时旧实现仍可能绿。应将“共享取号器”验成不依赖墙钟与机器速度的确定性回归。此项是测试护栏返修，不把历史 #14/#15 的原始失败擅自归因给它。

**当前状态**：两条遗留只记录了现象和「复跑变绿」；跨实例取号的修复已提交，但守住该修复的测试没有确定性反例。

**期望状态**：护栏在旧实例级取号器上确定性失败、在当前共享取号器上通过；历史两条各自要么有可重复的失败与对应修复，要么写明复核命令、次数与 revision 并继续观察，不因护栏返修而自动关闭。

## What Changes

- 除调查这两个历史测试外，仅返修 `UniqueSeqGuardTest`：用跨实例共享状态的确定性断言（可用反射比较两个实例取得的计数器对象身份），同时验证取到的名字不同；不得依赖同毫秒构造、睡眠、循环跑到偶然撞桶，也不得重置共享静态计数器污染其它测试。`IntegrationTestBase` 的已提交实现不因护栏返修而改动。
- 不顺手重构 `ScoreService` 或交卷路径。
- 先在当前已提交 HEAD 上重复运行历史两类（每类至少三次，逐次记录），记录失败或连续通过。连续通过不得写成「已修复」。
- 护栏须在隔离的旧实现工作树（`ed06f42` 的实例级种子 + 新护栏文件）稳定变红，在当前实现变绿；不要为了红测修改当前主工作树的基座，也不要把单次碰巧撞桶当确定性证明。
- 若能复现：修测试隔离或产品缺陷中被证据指到的那一处，并留下先红后绿。
- 若不能复现：在遗留条目写明尝试过的命令、次数和 revision，保持开放，不勾成完成。
- 本变更可在护栏确定性返修完成、定向与全量门禁通过且两条历史失败如实归类后归档；若历史两条未复现，#14/#15 继续开放，归档只代表护栏返修和观察方法收口，不代表两条偶发已修复。

## 时间线评估

小到中。护栏定向红绿可独立执行；两条历史测试逐次复核，若复现才深入根因。首次全量依赖与运行环境的耗时不预设。

## 风险

- 用 1000 次紧凑循环或一次红测声称“确定性”，旧实现可能因调度变慢而通过。缓解：护栏直接验证两个实例共享同一取号状态，并在旧实现工作树实跑红灯；不操纵系统时间或重置静态计数。
- 为了变绿而放宽断言。缓解：先红后绿必须对得上同一个失败信息；不能把期望改成「有时 4 有时 8」。
- 全量测试很慢。缓解：先重复失败过的测试类，再决定要不要全量。

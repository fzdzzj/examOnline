# 提案：监考总览先分账，再缩减答卷长字段读取

> 状态：待审批；代码与规范静态核对基于 `90222ef`（2026-09-26）。本提案不是已测得的监考性能缺陷。`docs/backend-optimization-candidates.md` 是更早 revision 的未跟踪候选台账，只作线索；执行时须重新核对 HEAD、工作树和规范。

## Why

`MonitorService.overview` 当前按考试调用 `submissionMapper.selectList`，未指定列投影，逐份载入完整 `ExamSubmission`。`schema.sql` 中同表有 `paper_json` 与 `answers` 两个 LONGTEXT。总览展示人数、状态、进度和异常，并只从答卷列表中**第一份非空个人快照**解析题目数；其余答卷的这两个长字段不用于总览逐人展示。轮询入口见 `MonitorController.overview`。

另一条独立成本是对每份进行中答卷调用 `draftService.get`，每次读取一份 Redis 草稿；在线状态已通过 `OnlinePresenceService.onlineOf` 的 MGET 批量查询，异常行为也是聚合 SQL。本轮不能先把 Redis 草稿改成批读，也不能把已经批读的在线状态再次列为 N+1。

**已验证**：上述控制流、列定义和已有 `AntiCheatIntegrationTest` 的权限/进度/异常场景。**未知**：实际班级规模和快照/答案大小、长字段在请求耗时/内存中的占比、Redis 草稿延迟以及投影增加一次窄查询后的净收益。历史交卷压测和隔离 H2 的排名测量都不是监考证据。最强反例是 Redis 逐人往返或其他聚合操作才是主因，或者额外 SQL 往返抵消字段节省；此时本提案不应实施投影。

## What Changes

1. 在**专用隔离环境**用固定人数、答卷状态比例、长字段大小和草稿内容建立可复跑的轮询基线，预热并逐轮记录请求 mean/p95/p99、吞吐、CPU/GC/峰值堆、响应体大小、答卷 SQL 耗时与返回行/字段量、Redis 草稿 GET 次数/耗时、在线 MGET 与异常 SQL。把字段量的估计值与真实网络传输字节区分开；H2/MockMvc 结果只代表该隔离口径，不能外推到 MySQL/Tomcat。
2. 先出 GO/NO-GO 裁决：只有多轮同负载证据表明答卷长字段读取是总览**占比最高的可控因素**，且可预期的收益明显超过轮间波动，才修改这一类数据库取数。若 Redis、CPU 或其他因素占主导、隔离 Redis/测量不可用，记录证据与未知，停在评估；另立变更讨论草稿批读，不顺手改。
3. GO 后把总览的逐人答卷查询限定到所需短字段，并用至多一次**独立的窄取数**保持从个人快照解析题数；不为每个学生回查快照，不在 SQL 投影里载入全部 `paper_json` 或 `answers`。须检查当前未指定排序下“第一份非空快照”的语义：空/全空/空白、损坏快照、题数不一致的异常数据不能因选取方式改变而悄悄换口径；无法等价时停止实施并如实说明。
4. 用相同数据、相同工具/预热/并发和多轮测量复验 SQL 与端到端效果；验证权限/归属、在线离线降级、已交卷进度、草稿近似进度、异常高亮与排序、返回形状不变。只有收益、语义与仓库根唯一门禁都成立才合入 delta 并归档；否则回退实现，保留评估证据，不把未采用条款写入基线。

## Impact

- **规范**：GO 且验收通过时，仅 `spec/specs/anti-cheat/spec.md` 的「监考大屏」Requirement 整段替换；保留两个既有场景，增加答卷取数边界场景。`spec/specs/performance/spec.md` 的先归因门禁已存在，不重复新增。
- **代码**：GO 后仅总览答卷取数路径（预计 `MonitorService`、如需独立窄查询则相应 Mapper）及针对性测试/隔离测量工具；`AntiCheatIntegrationTest` 作为既有回归基线。NO-GO 不改 `src/main`。
- **用户/API**：不新增端点、不改响应契约或用户可见口径；优化是否可感知须由同负载复测判定。
- **数据与部署**：不改 `schema.sql`、迁移、索引、JVM、线程池或 Redis 写入协议；不写共享 dev，不启 Docker，不做未经授权的跨宿主压测。

## 验收与停止条件

- 测量证据须绑定具体 revision、隔离环境、样本构造、命令、逐轮原始输出及已知干扰；请求墙钟分账、CPU 采样与字段大小估计的分母不同，不得直接当等值占比。
- 确定性护栏在旧代码下针对“总览主查询不载入长字段”先红，GO 后新实现转绿；同时覆盖缺快照、空白/损坏快照、不同题数快照、不同状态和归属拒绝。测试不依赖墙钟阈值；若原代码选择顺序未定义，不能凭一个插入顺序断言所有数据库上等价，需指出并验证实际适用语义。
- 若测得长字段并非主因、无法保真选快照、额外 SQL 抵消收益、或复测无可辨净收益：NO-GO/回退，不合入拟实施的 spec-delta，不标称已解决监考 P99。归档时如实标“未采用”或保留待决，步骤不适用不得伪造为已执行。
- 成功实施后在已提交的实现 revision 于仓库根执行 `mvnw.cmd clean test`（或 `./mvnw clean test`），记录当次四计数、BUILD 结论与退出码；记录 `AGENTS.md` 的 schema/@Sql/实体一致性自查。文档归档提交 SHA 不能自嵌，只引用门禁所跑实现 revision。

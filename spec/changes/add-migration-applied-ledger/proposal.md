# 提案：存量库迁移执行台账与核验（生产化 P2）

> 状态：已立项待执行；阶段 0 查证基于 main `c4425b0`（2026-10-11）现场重核。用户裁决授权（2026-10-11 AskUserQuestion）：执行侧**起 dev 容器做只读盘点 + 发现未应用缺口在同案内人工补应用并验证**（写 dev 库在授权内）。台账 `docs/production-hardening-candidates.md` 候选 P2 定性核对属实，其中优化点②「每脚本附幂等核验 SQL」部分失真——预期错误码语义已存在于各脚本头注惯例（1061/1068/1146），真实增量是集中式核验清单，且既有脚本按目录红线**不可改**。

## Why

- **现状（`c4425b0` 实测）**：`docker/mysql/migrations/` 有 11 个脚本（W7→W40）+ 完备 README（无自动执行者自述、`audit_log` 先例、手工应用流程 7 步）。流程第 7 步已要求记录「哪个库 × 什么时间 × 执行了哪几个脚本 × 验证输出 × commit」，但这些记录**散落在各归档变更 evidence 与决策记录的自然语言里**，无结构化「环境 × 已应用版本」载体；README 红线又明令不在该文件维护清单——登记表必须独立文件入库。这正是台账 P2 的核心增量。
- **不采信文献自述**：归档 evidence 里的「已应用」声称不可作为登记真值（与「子 agent 回报不是事实」同源纪律）；登记表须以**现场实测**（对 dev 主/从库逐脚本跑核验 SQL）为真值，文献记录仅作对照。dev 容器当前未起（在跑的是他项目 `sport-verify-*` 容器），起容器前须核对端口占用。
- **既有可复用资产**：README「什么时候需要脚本」场景表 + `verify-mysql8-init` 归档证据（空库 schema.sql 一次建全、存量迁移真跑 1068/1146 语义一致、`--force` 重复执行要点）已覆盖优化点③大半——runbook 整合引用，不重造。
- **spec 归属**：data-access 基线已有「新库建表可在 MySQL 8 执行」「AUTO_INCREMENT 列必须有主键」「索引变更先行核查」Requirement，存量库迁移台账是其自然补全。

## What Changes

1. **新文件 `docker/mysql/migrations/APPLIED.md`（迁移执行台账，入库，单文件承载三件事）**：
   - **登记表**：每脚本一行——脚本名、对象、幂等预期错误码、核验 SQL、dev 主库状态（已应用/未应用 + 核验输出摘要 + 核验时间 + 当时 commit）、dev 从库状态同构；脚本集与 `git ls-files docker/mysql/migrations` 恒对齐（表内不写计数）；
   - **集中核验清单**：即登记表内的核验 SQL 与预期结果列（优化点②的落地形态；不改既有脚本）；
   - **新环境从零建库 runbook**：可照做步骤（起库 → `schema.sql` 一次建全 → 何时无需迁移脚本 → 与 dev 一致性核验口径），引用 `verify-mysql8-init` 既有证据不复制数值结论；
   - **更新纪律**：此后每次人工应用完成 = 应用 + 执行后验证 + 更新本表三件套齐，git 历史即留痕。
2. **dev 现场盘点与补应用（用户授权范围）**：起 dev 容器（前置核对与 `sport-verify-*` 等在跑容器端口不冲突；只起本 compose 的服务）→ 逐脚本对主/从库跑核验 SQL（README 第 6 步口径：验证对象而非命令没报错）→ 已应用如实登记；**未应用缺口按 README 流程升序人工补应用**（对 master 应用，slave 先核复制状态——复制正常则由复制同步并复核，异常则停止上报不擅修）→ 逐脚本留「应用前状态 → 应用命令 → 应用后验证输出」链 → 停容器复原（他项目容器不触碰）。
3. **`docker/mysql/migrations/README.md` 与 `AGENTS.md`**：各加一行指针指向 APPLIED.md（只加指针不复制清单，尊重 README 红线与 AGENTS「不承载易变事实」纪律；AGENTS 硬约定 4 的出处段补该指针）。
4. **spec 基线**：`spec/specs/data-access/spec.md` 末尾 ADDED「存量库迁移执行台账与核验」Requirement（五 Scenario：登记表唯一结构化载体 / 现场实测优先于文献自述 / 应用后必须更新登记表 / 未应用缺口显性可见 / 新环境从零建库走 runbook）。

## Impact

- **规范**：data-access 能力域 ADDED 1 个 Requirement（五 Scenario）；既有 Requirement 零改动。
- **代码**：零业务代码（`src/`、`pom.xml`、`schema.sql`、`openapi.yaml`、`.github/` 均零触碰）；新增 APPLIED.md 1 文件；README / AGENTS 指针各 1 行；spec-delta 三件套。
- **环境**：dev 主/从库在授权内可能被写入（补应用）；dev 容器起停复原；`schema.sql`、H2 测试、他项目容器零触碰。
- **CI 影响**：纯文档笔，用例数与契约 paths 零变化 → `gate-baseline.json` 不动（合法持平）；本案验收以本地双端门禁为准（push 与 CI run 非本案必需，收口后 push 与 `c4425b0` 一并留待裁决）。
- **非目标（显式排除）**：任何自动执行机制（违反 AGENTS 约定 4 与 E1 决策）；Flyway / Liquibase；修改既有脚本（目录红线）；P3 部署形态与配置外置；生产环境（尚不存在）；修复主从复制故障（异常即停上报）。

## 验收与停止条件

- **本地**：双端门禁在实施笔前后持平全绿（零业务代码，数值不变）；AGENTS 四条自查 + 既有门禁自查全绿；APPLIED.md 不含连接口令/端口字面值（口令以 `application-dev.yml` 为准不复制，README 惯例）。
- **现场证据（三要素：命令 + 当次输出 + 短 revision，留存 measure 目录）**：盘点原始输出（每脚本核验 SQL + 结果 + 容器名 + 时间）；补应用脚本逐个完整链（前状态 → 命令 → 验证输出 → 登记更新）；主/从复制状态记录；停容器后 `docker ps` 复核他项目容器未受影响。
- **停止条件**：① 起 dev 容器遇端口冲突且无法在不动他项目容器的前提下解决 → 停止上报；② slave 复制通道异常（未同步且非脚本原因）→ 停止上报，不擅自修复制；③ 补应用遇到头注幂等说明之外的非预期错误码 → 停止上报，不得 `--force` 硬闯；④ 盘点发现 dev 实际结构与 `schema.sql` + 11 脚本预期存在**脚本外漂移**（手工改过的对象）→ 如实登记上报裁决，不擅自补写新脚本；⑤ 若完成登记须修改既有脚本或 README 红线 → 停止上报。

# 提案：在线考试与交卷链路（阶段 5，W4-W6 · 主战场）

## Why

考试管理就绪后，学生终于可以"进考场答题、交卷"。这是整个系统的核心闭环终点，也是面试弹药 B（可靠性工程）的代码载体——5000 人同时交卷不丢单、不重复、不串卷，全靠这一阶段的交卷链路设计。本阶段一次做完答题界面 + 交卷全家桶（幂等/MQ/超时双保险/自动保存/断线恢复），判分引擎留给阶段 6（本阶段交卷只存答案不判分）。

**背景**：
- 交卷可靠性决策已确认（`docs/需求决策记录.md` §1.1-§2.3、`docs/面试版实施方案.md` 深水区 1）：
  1. **三重幂等**：防重表 + `uk_exam_student` 唯一索引 + 分布式锁；
  2. **三路竞态**（手动交卷 / 前端倒计时归零强制提交 / 后端定时兜底）用 SETNX 一次性锁 + 状态机 CAS 保证只提交一次；
  3. **MQ 削峰**：交卷发消息、消费者批量落库（rewriteBatchedStatements），生产者 confirm + 消费者手动 ack + 死信重试；
  4. **自动保存**：30s Redis 草稿 + version 合并，断线恢复从草稿取回；
  5. **服务端时间为准**：前端倒计时仅展示，交卷/超时校验一律用后端时钟。
- 随机抽题/选项乱序**进入时锁定**（§3.4），满页刷新不换题；个人倒计时**点击开始才计时**（§7.9）。
- 切屏检测只警告+记录不强制交卷（§3.1），行为日志落库（anti-cheat 能力域的阶段 7 完整做，本阶段先埋切屏事件采集点）。
- 依赖阶段 4（add-exam-management）的考试快照与状态机。

**当前状态**：阶段 4 完成后有考试实体、状态机、考试快照，但学生无答题界面、无交卷能力，`exam_submissions` 表不存在。

**期望状态**：学生能进入考试、答题（导航/倒计时/自动保存）、交卷；交卷经幂等 + MQ 削峰可靠落库；超时三重兜底；断线可恢复；5000 人交卷高峰可压测证明不丢单不重复。

## What Changes

- **答卷实体**：`exam_submissions` 表（exam_id/student_id/start_time/submit_time/answers JSON/status/version + `uk_exam_student` 唯一索引）。
- **答题端**：考试列表（状态分组）、进入考试（生成个人快照锁定抽题/乱序 + 启动个人倒计时）、答题导航面板（已答/未答/标记）、倒计时（服务端时间为准）。
- **交卷链路**：
  - 幂等三层（防重表 + 唯一索引 + SETNX 锁）；
  - 三路竞态单次提交（手动 / 前端归零 / 后端定时兜底）；
  - MQ 削峰（交卷发消息 → 消费者批量落库，confirm/ack/死信）。
- **自动保存与断线恢复**：30s Redis 草稿 + version 合并，断线重进从草稿恢复。
- **切屏埋点**：答题页采集切屏/失焦事件，落 `exam_behavior_logs`（完整防作弊在阶段 7）。
- **交卷不判分**：只见客观题/主观题不在本阶段判，判分引擎阶段 6 承接。

## 风险

- **三路竞态重复提交** —— 缓解：SETNX 一次性锁 + `WHERE status='进行中'` CAS，状态只能"进行中→已交卷"一次。
- **MQ 丢消息/重复投递** —— 缓解：confirm + 手动 ack 落库后才 ack；消费端幂等（唯一索引拒绝第二次）。
- **长事务**（答案大 JSON 拖慢事务）—— 缓解：交卷主事务只落核心字段，批量插入 + rewriteBatchedStatements。
- **断线恢复答案冲突** —— 缓解：version + 时间戳合并，以最新为准并记录日志。
- **压测不达标** —— 缓解：W6 预留 JMeter 压测时间，P99<2s、0 丢单、落库<30s 为验收硬指标。

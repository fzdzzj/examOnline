# 提案：审计日志移出请求关键路径（audit-log-off-critical-path，P2）

## Why

`docs/submit-loadtest-report.md` §7.1 与判据 **G6**：`audit_log` 同步写在请求关键路径上（交卷等写操作的事务内/请求内落审计行），两个问题尚未单独评估：

1. 它是否值得移出关键路径（异步化），移出后请求时延收益多少；
2. 审计数据是否需要保留策略（无限增长 vs 定期清理）。

**保留策略部分与 `add-data-retention`（阶段 15，已归档）的 data-access 基线存在能力域重叠**——该基线已有「数据保留策略」「清理的删除条件必须索引可达」等 Requirement。本提案**只做查重与引用，不重复定义清理规则**；若结论是「audit_log 需要保留策略」，核对 data-access 基线是否已覆盖，覆盖则引用、不覆盖才在本提案的 spec-delta 里补。

**属后端独立立项**（改 `src/main` 与可能的迁移），不在前端阶段 19–23 串行链内。**这是门控提案**：先评估、后实施——评估结论若是「不值得移出」，如实关闭并记录，不硬改。

## What Changes

1. **评估（先行，有数字）**：现场测量 audit_log 同步写占关键路径的时延（如压测/微基准下含与不含审计写的对比，或 APM/慢日志证据），并盘点 audit_log 的既有调用点与失败语义（审计写失败当前如何处理：回滚业务？吞掉？）；
2. **实施（仅当评估结论 = 移出）**：审计写异步化（@Async / 事件 / 队列，按仓库既有异步风格），**审计不丢**（失败有补偿：本地暂存或重试或死信），业务事务不再等待审计落库；审计与业务最终一致性的边界如实声明；
3. **保留策略裁决**：对照 data-access 基线既有 Requirement 查重；若 audit_log 未被覆盖且确需清理，走该能力域的既有迁移与清理判据（索引可达、删的条件不扫全表）——**不另造规则**；
4. 测试：异步化后审计仍落库（含失败补偿分支）的集成测试；surefire 计数只增不减；
5. 性能证据：移出前后关键路径时延对比（三要素纪律）。

## Impact

### 受影响的规范
- `spec/specs/performance/spec.md` — ADDED：审计写入不占请求关键路径（条件于评估结论）。
- `spec/specs/data-access/spec.md` — 引用既有保留策略 Requirement（仅在需补 audit_log 条目时 MODIFIED）。

### 受影响的文件
- `src/main/**`（审计写入路径；以 `git grep -n "audit" -- src/main` 现场定位为准）
- `src/test/**`（新增测试）
- `docker/mysql/migrations/**`（仅当保留策略需要新列/索引；建表唯一入口 `schema.sql` 同步——AGENTS.md 硬约定 1/4）

### 需要迁移
- [ ] 数据库迁移（视保留策略裁决而定）

## 时间线评估

中：评估 0.5 天；若实施，异步化 + 测试 + 性能对比 1–2 天。

## 风险

- **审计不丢是底线**：异步化后审计丢失比重叠更糟——失败补偿分支必须有测试，否则宁可不移出；
- 异步审计的顺序性/可见性（教师刚操作完就查审计可能查不到）——如实声明延迟窗口，不假装即时；
- 与既有可靠性基线（`spec/specs/reliability/spec.md`）的异步链路要求对齐（消息确认、死信等既有判据适用则引用）；
- 评估若在共享 dev 栈上测，遵守错峰与复位纪律。

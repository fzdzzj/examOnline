# 提案：Java 优化必须先按同一负载归因（gate-java-change-on-measured-factor）

> 状态：待审批。本提案只建立门禁，不改 JVM，不改交卷代码。

## Why

没有同一负载下的延迟、吞吐和资源占用，就分不清时间在业务规则、数据库、远程调用、锁、CPU 还是 GC。本仓库上一次交卷复验已经说明：应用 CPU 不是主体，MySQL 在库内排队，而且压测进程和被测进程在同一台机器上。在调用次数和事务范围没有下降之前先调 JVM，违反这条纪律，也没有测量支持。

**当前状态**：交卷入口是 Redis 锁、幂等读写、状态 CAS 和 MQ 发送；答案落库在消费端按 JDBC batch 提交，不是按题发远程调用。这些是代码结构，不是本次延迟占比。

**期望状态**：任何 Java 优化先用同一基线量出占比，只改占比最高的一类，再用同一基线验收。指标不动就回到度量，不继续叠参数。

## What Changes

- 把上述纪律写成 performance 基线的需求。金额、库存、权限和幂等在本系统里对应分数、名额、权限和交卷幂等，不能为了变快改掉。
- 以交卷链路为第一条适用路径。引用既有容量复验作为「同机、应用参数已用尽」的历史基线，不把那次数字当成分离压测机之后的新结论。
- 在调用次数和事务范围没有下降证据之前，禁止改 JVM、堆、GC 或容器内存参数。
- 一次只允许一个因素。本提案自身不实施业务逻辑、SQL、锁或虚拟线程改动；某一类被证明占比最高后，另开一个变更。

## 风险

- 把历史同机 P99 当成已经归因到某一行 Java。缓解：本提案明确那次复验不能授权 JVM 或热点改写。
- 为了「做了优化」同时改 SQL、锁和线程池。缓解：一次变更只改一个因素，指标不动就停。

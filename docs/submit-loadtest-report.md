## 1. 结论摘要

| 硬指标 | 口径 | 结果 | 判定 |
| --- | --- | --- | --- |
| 提交 P99 < 2s | `label="POST /submit"` 逐笔 | 四轮 **2088 / 3522 / 3700 / 2200 ms** | **不达标**（四轮均超） |
| 0 丢单 | `status=2 AND answers IS NULL` | **0**（四轮均 0） | **达标** |
| 批量落库完成 < 30s | `MAX(updated_time) − MAX(submit_time)` | **16.0 / 2.0 / 19.0 / 16.0 s** | **达标** |

**P99 不达标的性质**：不是丢单、不是落库对不上、不是限流误伤，而是**在 200 线程的固定并发上限下，需求速率（≈490 req/s）超过了服务容量（≈455 req/s）**，差值 7% 在近饱和区被排队放大成 1.5–1.9 倍的尾延迟。详见 §4。

**一处重要的自我纠正**：第一次对比（run1 vs run2）曾把 P99 由 2088ms 恶化到 3522ms 归因于「调大消费并发/连接池」。补做的 A-B-A 对照（run3 恢复默认参数）**证伪了该归因**——真实主因是 **JVM JIT 预热状态**（冷 JVM ≈3.5–3.7s，热 JVM ≈2.1–2.2s），与容量参数无关。详见 §5。

## 2. 场景与数据

- **考试**：`LOADTEST-5000-并发交卷`，`published=1 status=1`，个人 deadline `NOW()+4h`（远晚于压测，避免 `ExamSweepService` 把答卷提前强制交卷污染采样）。
- **数据**：5000 个学生（`lt5k_0001`…`lt5k_5000`，`status=0` 正常）+ 5000 条 `status=1` 进行中答卷；造数脚本用**真实注册接口产出的 BCrypt 哈希**，与生产注册口径一致。
- **负载**：阶段 1 登录取 token（5000 线程 / ramp 30s，`SetupThreadGroup`，与提交串行）→ 阶段 2 交卷（5000 线程 / **ramp-up 10s**）。
- **为什么 ramp-up=10s**：交卷接口限流为**接口维度全局令牌桶** `capacity=2000 qps=500`，N 秒内放行上限 = `2000+500N`。10s 内到达 5000 笔 ⇒ 上限 7000 > 5000，429≈0。这是**场景整形**（模拟 5000 人陆续点交卷），**没有修改任何运行期限流参数**。若要观察限流拒绝语义，把 `SUBMIT_RAMP` 调小即可。

| 轮次 | 服务端 count | 服务端 sum | **服务端均值** | 隐含并发度 = sum÷墙钟 | 占 200 线程 | DB 丢单 | 落库尾巴 |

> **隐含并发度的含义**：Little 定律下「平均同时在应用内的请求数」= 服务端总耗时 ÷ 观测窗口。分母用的是**外部全程墙钟**（首请求发出→末响应返回），它 ⊇ 应用真正在处理的窗口，所以该比值只会**低估**并发度。四轮都得 ≥194.3，而 Tomcat 上限是 200 ⇒ **平均占用率 97%+，线程池全程饱和**。
>
> **run1 的 count=5039 与 run4 的扣减说明**：run1 的实例在正式轮之前还跑过 20 线程演练与冒烟请求，故累计计数为 5039（其中 20 笔演练样本合计仅 0.36s，对均值影响 0.017%，可忽略）；run4 与 run3 共用同一实例，Prometheus 计数器是累计值，表中已扣减前轮（`compare-runs.py` 自动处理并标注）。run3 的 4988 = 5000 − 12 笔客户端失败（见 §3.3）。

### 3.3 run3 的 12 笔失败：客户端资源耗尽，**不是服务端缺陷**

因果链完整闭合，服务端零责任：

```
宿主 TIME_WAIT 堆积 9531 条（临时端口耗尽）
  → 11 个「登录」请求 HttpHostConnectException（连都连不上）
  → tokens-run3.csv 只有 4989 行（5000 − 11）
  → 对应 11 个交卷线程取到空 token
  → 11 × HTTP 401，且全部集中在 t+10.34~10.36s 同一瞬间
  + 1 × java.net.BindException: Address already in use: connect（t+7.88s）
```

判定依据：**登录失败数(11) == 交卷 401 数(11) == token 缺失数(11)**；且这 12 笔**从未拿到 2xx**，按 §4 口径不构成丢单（DB 侧 `status=1` 残留 12 行、`丢单=0`，与样本完全一致）。

**基准方法学结论**：**连续压测会在客户端耗尽临时端口**，制造「假 401 + 抬高 P99」。规避：轮间等 TIME_WAIT 排空（实测 2 分钟内从 9531 降到 3329）、或让压测机与 SUT 分离、或复用长连接。

## 4. 瓶颈定位：线程池饱和 + 近饱和排队放大

### 4.1 证据链（四轮均可复算）

| # | 证据 | 数值 | 推论 |
| --- | --- | --- | --- |
| ① | `application*.yml` 中 **tomcat 关键字零命中** | — | 未配置过 ⇒ 取 Spring Boot 默认 |
| ② | 从构建实际使用的 `spring-boot-autoconfigure-3.5.5.jar` 探针读取 `ServerProperties` 默认值（探针已入库：`loadtest/probe/ProbeTomcatThreads.java`，跑法见文件头注释） | `threads.max=200`、`min-spare=10`、`accept-count=100`、`max-connections=8192` | 上限 = **200**（不是估的，是从库里的类读出来的） |
| ③ | 服务端 sum ÷ 外部墙钟（§3.2） | 194.3 / 194.5 / 195.4 / 194.4 | 平均占用 200 的 **97%** |
| ④ | 峰值 in-flight（逐笔还原） | run1 968、run2 1680 | 远超 200 ⇒ 大量请求在 Tomcat NIO poller 里**排队等线程**；这段等待**不计入**应用内计时器 |
| ⑤ | 应用内均值 vs 外部均值 | run1 439 vs 1515；run4 447 vs 1561 | 差值 ≈1.1s **就是排队时间**，不是处理时间 |
| ⑥ | `exam_submit_lock_wait_seconds` | 全部样本 ≤10ms（run1，`contentions=0`） | Redis 锁**不是**瓶颈 |
| ⑦ | Hikari `pending` | 各轮采样均 0 | 连接池未成为约束（**弱证据**：见 §6 取样限制） |
| ⑧ | 慢 SQL | run1/run3/run4 = 0 条 | 交卷路径 SQL 未超阈值 |

### 4.2 为什么 P99 恰好卡在 2s 附近

```
服务容量 = 线程上限 ÷ 单请求服务时长 = 200 ÷ 0.44s ≈ 455 req/s
场景需求 = 5000 笔 ÷ 10.2s         ≈ 490 req/s
490 > 455  ⇒  队列在整个突发窗口内持续增长（不会自愈，只会随窗口累积）

实测放大倍数（P99 ÷ 服务端均值，同一轮内自洽）：
  热 JVM  2088 ÷ 439 ≈ 4.8     2200 ÷ 447 ≈ 4.9
  冷 JVM  3522 ÷ 470 ≈ 7.5     3700 ÷ 520 ≈ 7.1
```

**要满足 P99 < 2s，需要 `200 ÷ 服务时长 > 500 req/s`，即服务端均值 < 400ms。** 热 JVM 实测 439–447ms，差距约 **10%**。

## 5. 基准方法学发现：JIT 预热主导了单轮结果（本报告最重要的教训）

四轮的 P99 与「实例 JVM 是否已预热」**完全同向**，与容量参数无关：

| 轮次 | 实例状态 | 服务端参数 | 服务端均值 | **P99** |
| --- | --- | --- | ---: | ---: |
| run1 | **热**（此前已跑过 20 线程演练+冒烟） | 默认 | 439ms | **2088ms** |
| run2 | **冷**（实例刚启动） | `RABBIT_BATCH_CONCURRENCY=8` `DB_POOL_MAX=40` `SLAVE_DB_POOL_MAX=20` | 470ms | **3522ms** |
| run3 | **冷**（实例刚启动） | 默认 | 520ms | **3700ms** |
| run4 | **热**（复用 run3 实例） | 默认 | 447ms | **2200ms** |

- **同参数、同场景，仅换 JVM 预热状态：冷 3700ms vs 热 2200ms（差 68%）。**
- **同为冷 JVM，换容量参数：3522ms vs 3700ms（差 5%，在噪声内）。**
- => run2 的「调参导致恶化」是**错误归因**；正确解释是「冷 JVM 服务端耗时 +7~18%，在 ρ≈0.93–0.97 的近饱和区被排队放大成 +60~77% 的 P99」。

**对后续所有压测的硬要求**：**先预热再测量**（正式轮前跑一轮小规模，或同实例连跑两轮取第二轮），且**每臂至少 3 轮取中位数**。本报告因单轮/臂，故**不给出任何参数效应的定量结论**。

## 6. 容量参数的作用边界（提案授权范围内的调参结论）

提案风险条款授权「不达标时先调容量参数（消费并发/批量/连接池）并复跑」。已执行（run2），结论是**该组参数不是交卷 P99 的杠杆**，但对**落库吞吐**是有效杠杆：

### 6.1 落库吞吐的容量模型定稿

`吞吐 ≈ 并发 × 批次大小 ÷ 单批耗时`，实测反解单批耗时：

| 轮次 | `RABBIT_BATCH_CONCURRENCY` | 批次大小 | 落库吞吐（5000÷尾巴） | 反解单批耗时 = 并发×批次÷吞吐 |
| --- | ---: | ---: | ---: | ---: |
| run1 | 1 | 100 | 5000÷16s ≈ **313/s** | 1×100÷313 = **320ms** |
| run2 | 8 | 100 | 5000÷2s ≈ **2500/s** | 8×100÷2500 = **320ms** |
| run3/run4 | 1 | 100 | 5000÷19s / 16s ≈ 263–313/s | ≈ 320–380ms |

**单批 100 行的落库耗时 ≈320ms，与并发无关；故落库吞吐 ≈ `并发 × 313 /s`，线性。** 8 倍并发实测得到 8 倍吞吐 —— 模型与实测自洽。

### 6.2 与连接池上限的联动约束

- 峰值连接需求 ≈ `RABBIT_BATCH_CONCURRENCY`（每个批量消费者占 1 条）+ Tomcat 工作线程的按需连接。
- 观测：`DB_POOL_MAX=40`（run2）与 `=20`（run1/3/4）时，**采样到的 `pending` 均为 0**，池未成为约束。
- **取样限制（必须声明）**：`hikaricp.connections.pending/active` 是**瞬时 gauge**，我采到的是突发结束后的快照，**无法回看峰值**。故「池未成为约束」是弱结论；要定量需要压测期间持续采样（已登记为后续动作）。

### 6.3 为什么它不影响交卷 P99

交卷接口的同步链路是「限流 → 三重幂等 → 状态机 CAS → **publish 并等 publisher-confirm**」，**不等消费落库**（答案由消费者异步批量写入）。因此消费并发/批量/连接池都不在交卷请求的关键路径上，调它们改变不了 439ms 这个服务时长。

## 7. 附带发现（均不在本变更授权内修改，登记为后续线索）

1. **`INSERT INTO audit_log` 在压力下可达秒级**：run2 出现 **17 条慢 SQL**，全部是这一条语句、耗时 1003–1145ms，且都发生在 `http-nio-8080-exec-*` 工作线程里（即**在请求关键路径上**）。run1/run3/run4 为 0 条。触发条件与宿主 IO/fsync 竞争相关；`audit_log` 目前**无保留策略**，持续增长。
2. **5000 并发登录把服务端打满 88.6s**：登录 P50 **33.5s / 35.5s**（run1/run2），`sum÷墙钟` 得并发度 ≥197.5（占上限 98.8%）。BCrypt 属 CPU 密集，登录接口**无独立限流**——从可用性视角，5000 并发登录即可让服务端 1.5 分钟内无法服务其它请求。本变更的硬指标只覆盖交卷，故仅记录。
3. **可观测性缺口三处**（这是「线程池饱和」这个系统级瓶颈至今无人看见的原因）：
   - Tomcat **线程指标未暴露**：指标栈里只有 `tomcat_sessions_*`，没有 `tomcat_threads_busy/config_max`。
   - `configprops`/`env` 端点未开放（仅 `health,info,metrics,prometheus`）⇒ 运行时**读不到** `server.tomcat.threads.max` 实际取值。
   - `exam_submit_duration_seconds` 是 **summary（只有 count/sum/max）、无直方图桶** ⇒ 服务端侧**算不出分位数**，只能拿平均值。
4. **`db/02-metrics.sql` 的 `clock_skew_s` 名不副实**：它算的是 `NOW() − MAX(submit_time)`，即**采样滞后**，不是「JVM 与 DB 的时钟偏差」（真偏差无法事后测）。实测值 10s/23s/26s 只是采样延迟。**这是本资产自身的口径缺陷**，应改名或改成断言形式。
5. **`_max` 取样陷阱**：run1 的 `exam_submit_duration_seconds_max` 读到 `0.0`、run2 立即读到 `1.88` —— 不是死指标，而是 Micrometer `TimeWindowMax` 的 2 分钟衰减窗口。**突发结束 2 分钟后再读 `_max` 会得到 0**，会误导判断。

## 8. 硬指标判定与后续

### 8.1 判定

- **0 丢单 / 批量落库 < 30s：达标**（四轮无一例外，且落库吞吐在调大消费并发后从 ≈313/s 提升到 ≈2500/s）。
- **提交 P99 < 2s：不达标**（四轮 2088–3700ms；最好的一轮 run1=2088ms 仍超 4.4%，最差的一轮 run3=3700ms 超 85%）。

### 8.2 为什么不在本变更修

P99 的绑定约束是 **Tomcat 线程上限**（Spring Boot 默认 200，全仓零配置）。调整它属于**改并发运行参数**，超出本变更授权（提案授权的只有消费并发/批量/连接池，且 §6 已证明三者不是该杠杆）。按任务边界「若暴露代码级瓶颈：登记为提案⑪的门控解除判据，不在本变更改实现」，仅登记。

### 8.3 提案⑪ 的门控解除判据（可直接作为其验收条件）

| # | 判据 | 依据 |
| --- | --- | --- |
| G1 | 说明并量化「服务端均值 < 400ms」或「提高线程上限」二选一的方案与代价 | §4.2：`200/服务时长 > 500 req/s` |

## 9. 复现步骤

见 `loadtest/README.md`。最短路径：

```bash
bash loadtest/prepare-data.sh                       # 造数，打印 exam_id
bash loadtest/run-loadtest.sh                       # 跑一轮（TAG=run）
python loadtest/analyze-results.py target/loadtest/submit-results-run.csv   # P99
mysql -h127.0.0.1 -P13316 -uroot -p exam_online < loadtest/db/02-metrics.sql # 丢单/落库时效
python loadtest/compare-runs.py run run2            # 多轮对比（含服务端/客户端并置与累计扣减）
mysql -h127.0.0.1 -P13316 -uroot -p exam_online < loadtest/db/03-cleanup.sql # 恢复环境
```

**压测期间必须复核的环境前提**：docker 栈（主库 13316 / 从库 13317 / RabbitMQ 5672）可用、Redis 可用；Docker Desktop 波动会导致宿主端口代理失效且映射错位，此时须 `docker restart <容器>` 后逐端口复核。

**原始产物去向**：每轮的逐笔 CSV、Prometheus 快照、DB 指标都落在 `target/loadtest/`，而 `target/` 同时是 Maven 构建目录——**跑 `mvn clean` 会把它们删掉**。本报告的表格是 `compare-runs.py` 的输出，可随时用上表命令重算；需要长期留档时应把 `target/loadtest/` 复制出工作区，不要指望它随构建存活。

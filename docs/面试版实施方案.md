# examOnline —— 面试版实施方案 v3（大厂面试级 · 深度优先）

> **编制日期**：2026-09-10
> **定位**：单体架构的**大厂面试级**工程实践。功能广度收敛，但每个环节按生产标准做：并发正确、故障可恢复、性能可证明、过程可观测。
> **架构**：单体 Spring Boot 3.5.5 + MySQL 8.0 主从 + Redis 7 + RabbitMQ + Vue3 + Nginx。
> **工期**：10-11 周（AI 辅助开发，1 人），深度不打折。
> **AI 协作模式**：AI 生成代码 → **人逐段理解消化后才提交**，每个深水区必须能自己讲三层。
> **核心叙事**：*"5000 人同时在线考试，交卷高峰不丢单、不重复、不串卷；每个故障场景都有兜底，每个性能结论都有压测数据支撑。"*

---

## 一、设计理念：三层深度模型

每个模块不是"功能做完"就结束，而是过三层：

| 层级 | 标准 | 例子（交卷） |
|---|---|---|
| **L1 功能正确** | 主流程跑通 | 学生能交卷、成绩正确 |
| **L2 并发与边界正确** | 极端场景不串、不丢、不重 | 双击/重试不重复、超时竞态只提交一次、并发批改不覆盖 |
| **L3 可观测、可恢复、可证明** | 出事能查、能恢复、能压测证明 | RequestId 全链路可查、MQ 重试/死信、5000 人压测报告 |

**面试价值**：L1 是人人都会的 CRUD；**L2+L3 才是区分度**。面试官问的"如果 X 失败会怎样"，全部对应 L2/L3。

## 二、范围（v3）

### 2.1 功能闭环（与 v2 一致，不再扩）

认证（双 Token/黑名单）→ 题库（CRUD/标签/软删）→ 组卷（手动/随机锁定）→ 考试（状态机/快照）→ 在线考试（倒计时/自动保存/交卷）→ 判分（客观自动 + 简答教师批改）→ 成绩（发布/导出）→ 防作弊（切屏/行为日志）

### 2.2 工程化维度（v3 新增，深度所在）

| 维度 | 内容 | 大厂面试点 |
|---|---|---|
| **可观测性** | RequestId 全链路日志、Micrometer 指标（QPS/延迟/队列积压）、关键事件落库 | 出问题怎么定位、怎么量化 |
| **可靠性** | MQ confirm/ack/重试/死信、幂等三重保障、乐观锁、分布式锁、定时兜底 | 故障怎么恢复、怎么防丢防重 |
| **性能工程** | 缓存 + 主从分离 + 批量插入 + 索引治理 + 限流 + 压测调优 | 容量怎么论证、瓶颈怎么找 |
| **测试** | 核心链路单元测试 + 集成测试（幂等/竞态/兜底） | 怎么证明"并发正确" |
| **工程化** | Docker Compose 一键部署、CI、多环境配置、优雅停机 | 部署/发布怎么做的 |

### 2.3 砍掉清单（同 v2）

Excel 导入、模板版本、复核/撤回、独立审计模块、重防作弊（人脸/设备/浏览器锁定）、离线模式、消息推送、练习/错题本/学情/排行榜。

## 三、四个深水区（大厂面试级，每个含"现实问题 + 技术方案 + 追问应答"）

### 深水区 1：交卷链路可靠性（⭐⭐⭐ 主战场，W7-9 三周）

**现实问题**（都是真实事故）：5000 人同时交卷 502/丢单；学生双击/弱网重试导致重复扣分；前端倒计时归零、后端定时兜底、手动交卷三路并发竞争；MQ 宕机/消息丢失/重复投递；断网重连丢答案；简答长答案大 JSON 落库拖慢事务。

**技术方案**：

| 问题 | 方案 | 追问应答 |
|---|---|---|
| 重复交卷 | 三重幂等：防重表（先查后插）+ `uk_exam_student` 唯一索引兜底 + 分布式锁 SETNX | 防重表与唯一索引各防什么：防重表拦并发窗口，唯一索引是最后防线 |
| 三路竞态（手动/超时前端/超时后端） | Redis `SETNX exam:{id}:{uid}:submit` 一次性锁 + 状态机 CAS（`UPDATE ... WHERE status='进行中'`） | 为什么不用纯应用锁：多实例部署要跨进程；CAS 保证状态只能从"进行中"→"已交卷"一次 |
| MQ 丢消息 | 生产者 confirm + 消费者手动 ack + 落库成功才 ack | ack 前宕机怎么办：未 ack 自动重回队列 |
| MQ 重复投递 | 消费端幂等（唯一索引拒绝第二次） | 为什么消费端还要幂等：MQ 至少一次投递语义 |
| 判分失败 | 标记"判分失败"入重试队列 + 死信 + 教师手动重判 | 重试 N 次仍失败：进死信队列人工补偿，不影响他人 |
| 长事务 | 交卷主事务只落核心字段；答案 JSON 与判分异步解耦；批量插入 500/批 + `rewriteBatchedStatements` | 长事务危害：锁持有久、连接池耗尽、主从延迟放大 |
| 断网丢答案 | 30s 自动保存 Redis 草稿 + version 合并 | 草稿与正式提交的关系：草稿是"未提交态"，正式提交才锁死 |

### 深水区 2：认证与安全（⭐⭐ W1-2）

**现实问题**：Access Token 泄露被冒用；学生改密码后旧 Token 仍有效；老师 A 改老师 B 的试卷（水平越权）；暴力破解。

| 方案 | 追问应答 |
|---|---|
| 双 Token：Access 30min + Refresh 7d，Refresh 轮换（旧 Refresh 作废） | Refresh 被偷怎么办：轮换 + 复用检测（发现旧 Refresh 复用即全端下线） |
| Redis 黑名单（jti）：登出/踢人/改密码入黑名单至过期 | 为什么不用 JWT 注销标准：无状态 Token 只能靠黑名单主动失效 |
| 登录锁定：5 次错误锁 15 分钟（Redis 计数） | 绕过方式：换 IP 攻击 → 配合账号维度锁定 + 限流 |
| 水平越权防护：Service 层 `assertTeacherOwnsExam(uid, examId)` | 为什么不只靠前端隐藏按钮：接口可被直接调用，权限必须在后端 |
| 角色 AOP：`@RequireRole` 注解 + 切面校验 | 与 Spring Security 对比：轻量够用、学习成本低，讲清取舍 |

### 深水区 3：数据一致性与模型（⭐⭐ W5-6、W10-11）

**现实问题**：考中改题污染已考答卷；随机抽题刷新后题目变了（可刷题）；两个老师同时批改同一份答卷互相覆盖；成绩发布与批改竞态。

| 方案 | 追问应答 |
|---|---|
| 试卷快照：发布时序列化试卷 JSON 入快照表，答卷/判分/回看只读快照 | 快照多大/存储：5000 人 × 50 题 JSON ≈ 几百 MB/场，可接受；只写一次无缓存一致性问题 |
| 抽题锁定：进入考试生成个人快照并锁定 | 与试卷快照区别：试卷快照防"改题"，个人快照防"换题" |
| 乐观锁：`exam_submissions.version`，批改/发布 `UPDATE ... WHERE version=?` | 冲突怎么办：失败重试或提示"已被他人批改"，绝不静默覆盖 |
| 软删除 + 快照隔离：题目软删，历史答卷可回看 | 软删与硬删权衡：数据量、审计、历史完整性 |
| 答案存储：`answers` JSON（客观题）+ 简答明细表 | 什么时候该拆表：>100KB 大文本/需要逐题查询统计时拆 |

### 深水区 4：性能与可观测性（⭐⭐ W13-15）

**现实问题**：主从延迟导致刚交卷查不到成绩（读己之写）；开考瞬间缓存穿透 DB 被打爆；队列积压；导出大 Excel OOM；连接池耗尽雪崩。

| 方案 | 追问应答 |
|---|---|
| 主从读写分离 + 读路由：刚提交/刚发布的查询强制走主库 | 怎么识别"刚写"：ThreadLocal 标记 + 短时间（如 2s）路由主库 |
| 缓存：试卷快照/考试信息缓存 + 空值缓存防穿透 + 随机过期防雪崩 | 为什么快照不会不一致：发布后只读不写，天然最终一致 |
| 限流：交卷接口令牌桶（如 2000/s）、登录接口限流 | 限流与削峰关系：限流挡在网关层，MQ 削峰在应用层，双层 |
| 导出防 OOM：SXSSF 流式写 + 分批查询 | 5000 行也 OOM？：POI 默认全量载内存，必须流式 |
| 可观测：RequestId 全链路 + Micrometer（QPS/延迟/队列深度）+ 慢 SQL 日志 | 压测时怎么定位瓶颈：指标四件套——CPU/连接池/队列深度/慢 SQL |
| 优雅停机：先停 MQ 消费者 → 完成在途事务 → 再停 HTTP | 停机丢消息吗：消费者停前 drain，未 ack 消息重回队列 |
| 压测：JMeter 模拟 5000 并发交卷，产出报告（吞吐/延迟/P99/错误率） | 报告怎么证明容量：P99 < 2s、0 丢单、落库完成时间 < 30s |

## 四、数据库核心表（v3 与 v2 一致，加版本字段说明）

```sql
users(id, username, password, name, role, created_time, is_deleted)
questions(id, type/*1单选 2多选 3判断 4简答*/, content, choices/*JSON*/,
          correct_answer, score, difficulty, analysis, created_by, created_time, is_deleted)
tags(id, name, type, created_by)
question_tags(question_id, tag_id)
papers(id, title, description, total_score, created_by, created_time, is_deleted)
paper_questions(id, paper_id, question_id, number, score)
exams(id, title, paper_id, course_id, class_id, start_time, end_time, duration_minutes,
      status/*0未开始 1进行中 2已结束 3已批改 4已发布*/,
      anti_cheat_config/*JSON*/, allow_late_minutes, created_by, created_time, is_deleted)
paper_snapshots(id, exam_id, paper_json, version, created_time)     -- 试卷快照（发布时生成）
exam_submissions(id, exam_id, student_id, start_time, submit_time,
      answers/*JSON*/, objective_score, subjective_score, total_score,
      is_submitted, is_graded, status, version/*乐观锁*/,
      UNIQUE KEY uk_exam_student (exam_id, student_id))             -- 幂等最后防线
subjective_grades(id, submission_id, question_id, score, comment, graded_by, graded_time)
exam_behavior_logs(id, exam_id, student_id, event_type, event_data/*JSON*/, severity, event_time)
courses(id, name, term, created_by) / classes(id, course_id, name)
course_teachers(course_id, teacher_id) / class_students(class_id, student_id)
```

## 五、里程碑（10-11 周，AI 辅助版）

> AI 写码效率按 2-3 倍算，但每个模块保留"消化验收"：**AI 产出 → 人通读 → 改注释/补测试 → 才提交**。
> 每天固定 1-2 小时消化时间，深水区模块（交卷链路）消化时间加倍。

| 阶段 | 内容 | 消化验收标准（L3） |
|---|---|---|
| W1 | 骨架 + 认证（双 Token/黑名单/角色 AOP） | 能讲清 Refresh 轮换与黑名单实现 |
| W2 | 题库 + 组卷（手动/随机锁定） | 能讲清个人快照如何防换题 |
| W3 | 考试管理 + 状态机 CAS + 试卷快照 | 能讲清快照与 CAS 的关系 |
| W4-6 | **在线考试 + 交卷链路（深水区 1，3 周）** | 三重幂等/三路竞态/MQ 重试死信/断线恢复，**逐行能讲** |
| W7 | 判分（策略模式）+ 简答批改（乐观锁）+ 成绩发布导出（SXSSF） | 能讲清并发批改防覆盖 |
| W8 | 防作弊（切屏策略模式 + 行为日志） | 能演示新增事件类型不动核心 |
| W9 | 主从读写分离 + 读己之写 + RequestId/指标 + 限流 + 优雅停机 | 能讲清"刚交卷查主库"路由 |
| W10 | JMeter 压测 5000 + 调优 + Docker Compose + CI | 压测报告达标；一键起 |
| W11 | 面试文档汇总（每模块深水区问答）+ 演示打磨 + 面试模拟 | 追问三层能答 |

**每周固定节奏**：
- 周一：规划本周模块，拆 AI 提示词任务；
- 周二-五：AI 生成 → 人消化 → 提交（深水区周放慢，宁缺勿滥）；
- 周五：写该模块"现实问题 → 方案 → 追问应答"进面试文档；
- 周日：本周代码自测（并发/边界场景手动跑一遍）。

**纪律（防"AI 写了个能跑的但你不懂"）**：
1. 每个 PR 必须包含 AI 生成代码 + 你的理解注释/重构，禁止原样盲提交；
2. 深水区代码（锁/幂等/MQ）必须手写时序图后再写实现，AI 只做校验；
3. 面试文档与代码同步更新，W11 只汇总不补写。

## 六、面试叙事（v3 升级版）

**开场 30 秒**：*"我用单体架构做了一个支撑 5000 人同时在线考试的 examOnline。技术上重点做了三件事：①交卷链路的三重幂等 + MQ 可靠投递，保证高峰不丢单不重复；②JWT 双 Token + Redis 黑名单的安全体系；③试卷快照与乐观锁，保证改题不污染历史、并发批改不覆盖。全部经过 JMeter 5000 人压测验证。"*

**三层应答结构**（每点都按"做了什么 → 为什么这么设计 → X 失败会怎样"准备）。

**诚实边界**：明确说"微服务/分库分表评估过，5000 人单体够用，拆的时机是 10 万级或多人团队"——体现架构判断力而非堆技术。

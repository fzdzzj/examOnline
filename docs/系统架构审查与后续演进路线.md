## 一、 审查背景与核心定位

本项目定位为**大厂面试级、高可靠性单体在线考试系统**，叙事核心为：
> *“5000 人同时在线考试，交卷高峰不丢单、不重复、不串卷；每个故障场景都有兜底，每个性能结论都有压测数据支撑。”*

系统严格遵循三层深度模型：
- **L1 功能正确**：业务闭环正常跑通；
- **L2 并发与边界正确**：并发、幂等、竞态、超时、网络分区、组件故障下行为可解释；
- **L3 可观测、可恢复、可证明**：指标监控、链路跟踪、对账机制、运行态演练证据与压测报告。

本次审视旨在全面排查**不合理的设定、隐藏的并发/性能/安全隐患**，并梳理最具区分度与落地价值的**后续演进路线图**。

## 二、 架构与设定层面的局限与权衡

### 1. 读己之写（Read-Your-Write）依赖 `ThreadLocal` 在真实 HTTP 请求间失效
- **代码实现**：[`ReadYourWriteMark`](file:///d:/code/examOnline/src/main/java/com/exam/config/ReadYourWriteMark.java) 与 [`ReadYourWriteRouter`](file:///d:/code/examOnline/src/main/java/com/exam/config/ReadYourWriteRouter.java)。
- **机制原理**：在完成写操作（如交卷/发布/批改）后，在当前线程留下一枚时间戳（5000ms 窗口），窗口期内该线程执行 `@DS("slave")` 时强制压栈切回 `master`。
- **现实局限**：
  - 在前后端分离的 RESTful 架构中，客户端发起的写请求由 Tomcat 线程池的线程 A 处理，处理完毕后线程归还池并清理；
  - 随后客户端紧接着发起的重定向或查询请求（如查看成绩、答卷详情）会被分配到线程 B，线程 B 的 `ThreadLocal` 为空，无法识别该用户刚刚发生过写操作；
  - 虽目前代码中大部分读端点本就默认路由 `master`（全仓仅 3 处使用 `@DS("slave")`），但若在架构面试中声称「基于 ThreadLocal 解决了主从复制延迟下的读己之写」，在理论上是不成立的。
- **演进方案**：
  - **方案 A（轻量客户端驱动）**：写操作成功后，响应头携带 `X-Write-Timestamp: <ms>`，客户端在后续请求中携带该 Header；网关或统一拦截器解析若在 5s 内，则为该次请求上下文打上走主库标记。
  - **方案 B（服务端分布式标记）**：写操作完成后在 Redis 写入 `user:{id}:last_write_at`（TTL 5s），拦截器读取并判断是否强制路由主库。

### 2. 定时调度多实例完全无锁，依赖下游短事务竞争
- **代码实现**：[`ExamStateMachineService`](file:///d:/code/examOnline/src/main/java/com/exam/exam/service/ExamStateMachineService.java)、[`ReservationRemindService`](file:///d:/code/examOnline/src/main/java/com/exam/message/service/ReservationRemindService.java)、[`ExamSweepService`](file:///d:/code/examOnline/src/main/java/com/exam/taking/service/ExamSweepService.java)、[`RetentionService`](file:///d:/code/examOnline/src/main/java/com/exam/monitoring/retention/RetentionService.java)。
- **机制原理**：不引入 ShedLock / Quartz / Redisson 等外部调度锁，多实例下各实例均执行 `@Scheduled`，依赖下游 CAS、唯一键及幂等设计保证数据正确性。
- **潜在隐患**：
  - 状态机轻量轮询代价较小，但 [`ExamSweepService`](file:///d:/code/examOnline/src/main/java/com/exam/taking/service/ExamSweepService.java) 单轮拉取 500 条超时候选、[`RetentionService`](file:///d:/code/examOnline/src/main/java/com/exam/monitoring/retention/RetentionService.java) 凌晨批量短事务清理历史记录时，多节点并发拉取相同区间执行 `UPDATE / DELETE`，极易在 MySQL InnoDB 层面诱发间隙锁/行锁竞争（Lock Wait Timeout）甚至死锁（Deadlock）。
- **演进方案**：
  - 引入**非侵入式、Fail-Open 的轻量 Redis 分布式调度锁**：
    - 采用 `SET exam:sched:lock:{job} {nodeId} EX {ttl} NX`；
    - 抢锁成功的节点执行调度，抢锁失败则静默跳过；
    - **Fail-Open 铁律**：若 Redis 发生异常，捕获异常并降级为“放行执行（退化为当前的幂等多实例运行）”，绝不因 Redis 故障导致超时收卷或数据清理停摆。

### 3. 题干图片本地文件存储（多容器扩容限制）
- **代码实现**：[`QuestionImageController`](file:///d:/code/examOnline/src/main/java/com/exam/question/controller/QuestionImageController.java) 与 [`QuestionImageDownloadController`](file:///d:/code/examOnline/src/main/java/com/exam/question/controller/QuestionImageDownloadController.java)。
- **现状**：图片存储在本地目录 `${exam.question-image.dir:./data/question-images}`，下载端点直接读取本地文件系统。
- **现实局限**：在单机 Docker Compose 场景下可通过宿主机挂载卷工作，但在真实多实例容器集群（Kubernetes / Docker Swarm）弹性扩缩容时，必须挂载共享网络存储（NFS/Ceph）或适配 S3 / MinIO 对象存储接口，否则不同节点间存在文件可见性孤岛。

## 三、 性能瓶颈与高并发深水区

### 1. 5000 并发压测 P99 延迟偏高（2~3s）
- **历史证据**：见 `docs/submit-loadtest-report.md`，压测证实「0 丢单、批量落库 < 30s 达标」，但「交卷接口 P99 延迟达 2088~3700ms」。
- **瓶颈归因**：
  1. **资源争抢**：压测机 JMeter 与 被测系统 SUT（Spring Boot + MySQL + Redis + RabbitMQ）同宿主运行，严重争抢 CPU 与磁盘 IO；
  2. **大 JSON 内存分配**：`exam_submissions.answers` 和 `paper_json` 为全量明细的大字符串，5000 人并发提交造成 JVM Young 区对象频繁分配，GC 停顿拖慢 P99；
  3. **MySQL 排队**：数据库 `Threads_running` 飙升至 57~103，连接获取与事务提交排队。
- **改善空间**：
  - 客观题答案只存精简 map `{"1":"A","2":"BC"}`，大题主观题作答与题干分离；
  - 生产化部署时压测机必须与宿主机物理隔离。

### 2. 存量无时间索引表的长期膨胀风险
- **表现状**：
  - `user_messages`（站内消息表）：仅有复合索引 `(user_id, id)`，缺少时间列索引，目前被规范禁止发起全表扫 DELETE；
  - `practice_attempt`（错题重练作答明细）：仅有 `(student_id, question_id, id)`，学生每重做一题即插入一条，无归档策略。
- **风险**：随着系统长期运行，单表数据量将单调递增，未来按用户查消息或查练习记录时的 B+ 树层级和扫描行数会逐步恶化。

## 四、 安全边界与风控漏洞

### 1. 注册端点（`/api/auth/register`）缺乏频控，存在 CPU 耗尽 DoS 风险 🔴
- **代码实现**：[`AuthController.register`](file:///d:/code/examOnline/src/main/java/com/exam/auth/controller/AuthController.java#L44-L48) $\to$ [`AuthService.register`](file:///d:/code/examOnline/src/main/java/com/exam/auth/service/AuthService.java#L131)。
- **漏洞分析**：
  ```java
  user.setPassword(BCrypt.hashpw(req.getPassword(), BCrypt.gensalt(12)));
  ```
  BCrypt `gensalt(12)` 计算单次耗时约 200~300ms，CPU 开销极大。
  与登录接口配有 `loginGuard.checkRateLimit` 不同，**注册端点当前完全没有限流保护（无 `@RateLimit`、无 IP 频次拦截、无图形验证码）**。
- **攻击场景**：恶意用户或脚本只需发起并发 10~20 的循环注册请求，即可将服务器所有 CPU 核心打满至 100%，造成全站业务（包括正在进行的考试答题、交卷、鉴权）因 CPU 饥饿全面瘫痪。
- **整改方案**：
  - 为 `register` 端点补充基于客户端 IP 的限流注解 `@RateLimit` 或服务层 Redis 令牌桶；
  - 限制同 IP 在 1 分钟内的注册尝试次数（如 ≤ 5 次/分钟）。

### 2. 监考大屏依赖客户端轮询，缺乏实时事件下推
- **代码实现**：前端监考页面每 10 秒主动调用一次 overview 接口。
- **现状分析**：切屏（`SWITCH_SCREEN`）、离开全屏（`FULLSCREEN_EXIT`）等行为由考生端上报后即刻落表，但教师端由于依赖 10 秒轮询，感知存在显著滞后；且考场考生量大时，定时轮询给后端造成了不容忽视的只读 QPS 压力。
- **演进方向**：引入轻量级 Server-Sent Events (SSE) 或 WebSocket 实现重要作弊预警的秒级单向实时下推。

## 五、 后续高价值特性演进路线图

按照业务价值、技术区分度及落地复杂度，整理出 5 个优先候选卡：

```
[优先级 1] 注册端点防刷与 CPU 保护 (安全加固)
   ↓
[优先级 2] 考中应急管理：考试全场/个人顺延与补时机制 (核心业务深水区)
   ↓
[优先级 3] 考试分析报告引入「试题区分度 (D值)」与信度模型 (创新点 4 深度拓展)
   ↓
[优先级 4] 错题智能掌握消除与一键组卷强化复习 (学生端学习闭环)
   ↓
[优先级 5] 简答题双评盲评与分差仲裁工作流 (大考级主观题批改)
```

### 候选 1：注册端点防刷与 CPU 保护（安全加固 · S 级）—— 【✅ 已落地合入主干】
- **归档变更**：`harden-register-rate-limit`（合入提交 `main@24bc3ad`，2026-10-18）。
- **落地内容**：
  - 后端：在 `LoginGuardService` 接入 `checkRegisterRateLimit(ip)`，60s 固定窗口限流（默认 10 次/分）；Redis 异常时走 fail-open 降级并打点 `exam.auth.degraded`；
  - 契约与门禁：新增单测与集成测试 7 例（740→747），OpenAPI 101 paths 不变，变异验证 m1/m2 均断言级击红留证。

### 候选 2：考中应急管理 —— 全场/个人顺延考试时间（核心业务 · S 级）—— 【✅ 已落地合入主干】
- **归档变更**：`add-exam-time-extension`（合入提交 `main@eabcb87`，2026-10-18）。
- **落地内容**：
  - 接口契约：新增 `POST /api/exams/{id}/extend-time`（101→102 paths），权限 `exam:manage` 并做归属校验；
  - 双模式执行：全场模式顺延 `exams.end_time`/`duration_minutes` 并批量顺延所有进行中答卷，个人模式仅顺延指定考生在途答卷；使用 MySQL 8 与 H2 双端兼容的标准 SQL `TIMESTAMPADD` 函数原子累加，零 DDL；
  - 审计与通知：记录 `EXAM_EXTEND_TIME`（`VARCHAR(32)` 原生容纳）安全审计日志；旁路向真正受影响考生投递延时站内通知（try-catch 吞异常不阻断主事务）；
  - 门禁与验证：新增单测与集成测试 14 例（747→761 全绿）；三变异 m1/m2/m3 全部断言级击红并回绿留证。

### 候选 3：考试分析报告 —— 试题区分度（Discrimination Index）与信度分析（业务创新 · S 级）
- **业务场景**：教师与教学管理者评估试题命题质量，识别好题、坏题及有歧义题目。
- **方案设计**：
  - 经典测量学算法：
    - 将考生按全卷总分排序，截取前 27% 为高分组（High Group），后 27% 为低分组（Low Group）；
    - 逐题计算区分度：$D = P_H - P_L$（高分组得分率减低分组得分率）；
    - 评价等级标记：$D \ge 0.40$（优良）、$0.30 \le D < 0.40$（良好）、$0.20 \le D < 0.30$（可接受/需微调）、$D < 0.20$（劣质/无区分力/题干歧义）；
  - 呈现与导出：在既有的 `ExamAnalysisReportService` 及多 Sheet 导出中，在「逐题指标」工作表追加预估难度、区分度及质量评价建议。

### 候选 4：错题智能掌握消除与一键组卷强化（学习闭环 · M 级）
- **业务场景**：解决当前学生错题重练正确后仍无法从错题本中消除的问题。
- **方案设计**：
  - 状态演进：错题增加掌握状态维度（待攻克、攻克中、已掌握）；
  - 消灭规则：错题单题重练连续正确 2 次（基于 `practice_attempt` 判定）自动标记为「已掌握」；
  - 错题强化卷：支持「一键复习」，自动从错题库抽取 10 道待攻克题目动态生成一份自测小练习。

### 候选 5：简答题双评盲评与分差仲裁机制（大考架构 · M 级）
- **业务场景**：模拟高考、考研等高严肃性考试的主观题批改流程。
- **方案设计**：
  - 试卷/考试启用双评模式：系统为每份主观题随机分派给两位教师（背靠背匿名打分）；
  - 裁决规则：若 $|Score_1 - Score_2| \le \text{Threshold}$，终分取两评平均值；若分差超标，自动流转至仲裁队列，由教研组长终审裁决。

## 六、 结论与建议

当前系统基线极其稳固（双端门禁 740 后端 / 943 前端 / 101 paths 全绿）。
建议根据下一阶段的战略侧重点进行选择：
1. **若追求系统安全风控无死角** $\to$ 首选 **候选 1（注册端点 CPU 防 DoS 频控）**；
2. **若追求业务实战深度与大厂面试最佳故事线** $\to$ 首选 **候选 2（考中应急顺延与个性化补时）**；
3. **若深化数据智能与分析专业度** $\to$ 首选 **候选 3（试题区分度 D 值与质量分析）**。

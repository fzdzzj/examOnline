# 指导主 Agent 执行指南

> 适用范围：主 Agent 负责项目判断、方案与验收把关；实施优先交给用户安排的低成本子 Agent。本文件是**角色与协作方法**，不是项目进度、环境或门禁的事实源。旧 `docs/指导Agent交接文档.md` 保留为历史记录与本机踩坑索引，但其中的「下一步」「当前」和未收口结论不得直接继承。

## 1. 职责与权限

- **我负责**：查证需求与现状；找反例、隐含前提和风险；提出有排序、有取舍的优化或修复建议；制定可独立验收的边界；审阅子 Agent 产物并指出下一步。不是“需求越多越好”，也不把“计划写完”当作“问题解决”。
- **用户负责**：确定优先级、不可逆或影响产品语义的取舍、预算/权限；决定用哪个模型或平台执行。给出有依据的推荐方案和备选项，**只在确需裁决时提问**，不把小的可逆选择都推给用户。
- **子 Agent 负责**：经用户授权后，在指定文件范围内实施、写必要测试、报告命令与原始结果；不因本指南而自动获得改代码、跑共享环境、提交或部署的权限。主 Agent 不默认亲自实现，不为“保持忙碌”派工。
- 仓库既有硬约定、变更工作流和唯一事实源分别以 `AGENTS.md`、`spec/README.md`、`README.md` 的路由为准；本文件不复制其内容。冲突时先核对代码和更近的事实源，不用本文件改写既有约定。

## 2. 对旧指导方式的校正（不是全盘否定）

| 旧做法或失效模式 | 证据与判断 | 新做法 |
|---|---|---|
| 把长交接当实时路线图 | 旧文档 §5.2 仍称 MySQL 初始化/存量迁移未验证，§6.2 仍把确认异常称为待修；`spec/README.md` 的归档记录已分别登记真机验证和确认修复。历史陈述有原时点的价值，但**不能推成现在未完成**。 | 当前状态只查 `spec/README.md`、目标变更的 `tasks.json` 和代码；历史段落只用于追因，冲突明确标时点。 |
| 把子 Agent 自述或测试表面全绿当交付 | `spec/README.md` 的前端验收事故记录了未验收先入库、串接符吞退出码等反例；旧交接也要求独立看 diff。 | 验收查实际改动归属、关键行为和本次执行证据；做不到就标“未验证”，不替子 Agent 补编结论。 |
| “每个子 Agent 必须自己 commit”、一律自包含派工提示词、固定最多返修次数 | 旧交接 §7 有此类一刀切要求。它们在界定责任时可能有用，但并非每次分析、文档审阅或未提交的中间片都适用；一律重述仓库规则会重复上下文。 | 任务只给必要范围和验收判据；**由任务约定谁提交及何时提交**，最终验收仍需绑定实际 revision；返修以新证据和停止条件裁决，不设无依据的统一次数。 |
| 把必要的独立核验扩大为事事立项、每轮全量重跑 | 旧交接 §7–§8 的独立核验值得保留；但 `spec/README.md` 规定的是“开发阶段=变更”与**声称验收时**的证据纪律，不能推导出每个咨询问题都要新建变更并跑全量门禁。此项是防止误用，并非声称旧主 Agent 每次都这样做。 | 先做最小充分验证；进入已批准的实施阶段再按该变更的步骤和验收门禁执行，不用省钱为由跳过真正需要的验收。 |

上述是协作方式调整，不是否定旧文档中已被仓库规则采纳的约束：例如不能让 `@Sql` 掩盖建表问题、不能以迁移脚本提交冒充存量库已迁移、同一工作树不能让两个实施 Agent 同时写。

## 3. 每次请求的最小闭环

1. **定问题**：把用户的诊断/方案视为假设；明确目标、成功条件、是否仅需建议，以及哪些地方需要用户拍板。不要擅自扩大到“顺手重构”。
2. **读证据**：从 `README.md` 路由到相关 spec、变更和代码；先用窄范围搜索、可复现测试或运行结果检验关键前提。对于会导致方案失败的反例，先查再推荐。记录“已核实 / 推断 / 未知”，区分旧文档快照与当前状态。
3. **给决策**：默认先交付结论、推荐方案、边界、代价/风险和验收办法；优先解决可复现缺陷或关键路径证据缺口，避免为展示技术而扩大架构。新阶段是否立项依 `spec/README.md`，不要把一段分析自动升级成提案或开发。
4. **决定是否派工**：只有实施已获同意且任务范围清楚时，选择第 4 节的交付形式。用户明确要主 Agent 只指导时，不自行修改业务代码或代子 Agent 交付。若发现与原目标冲突的高风险事实，先暂停该分支并说明证据。
5. **按结论强度验收**：咨询类只需核对论据与文件指向；小改动检查实际 diff + 相关测试；阶段收口还须按 `spec/README.md` 的工作流核对已提交状态上的门禁与证据字段。每次声称“通过”都附该次命令、真实输出和 revision；未跑不写“全绿”。

## 4. 怎么让便宜子 Agent 做事，而不让提示词吃掉预算

### 4.1 任务分级流转（拒绝形式主义三段式）

根据变更的**影响面与风险等级**分级派工，坚决避免所有小功能一律启动「实施-复核-收口」三轮子 Agent 的算力与人力浪费：

- **S 级轻量任务（纯文档/治理/配置微调/小残差修复/文件数 < 5）**：
  - **模式**：**单 Agent 一票到底**。
  - **流程**：实施子 Agent 完成先红后绿自测，直接在分支完成 `--no-ff` 合并、spec 归档与 tasks.json 回填。
  - **验收**：主 Agent 自行核对最终 diff 与 CI 状态即可宣布收口，**不派发独立的复核子 Agent 与收口子 Agent**。
- **M/L 级业务变更（并发控制/破坏性 DDL/状态机/交卷判分核心链路）**：
  - **模式**：**双岗隔离，收口自动化**。
  - **流程**：实施子 Agent 完成自测提交待复核状态；独立复核 Agent 负责红线域比对与变异自证。
  - **收口**：复核判定 PASS 后，收口动作（合入基线、三件套归档、合并合流）由主 Agent 直接执行或脚本化一键完成，**不再启动第三轮收口子 Agent**。

### 4.2 极简派工卡协议（字数严格限制在 300 字内）

**主 Agent 严禁在聊天会话中全量复制仓库规则**：严禁复述 `AGENTS.md` 四条硬约定、严禁粘贴变异五步法操作手册、严禁贴几千字长篇汇报模板。所有通用约束由子 Agent 从版本库文件自行读取。

主 Agent 派发任务统一采用**参数化极简派工卡**：

```text
【派工：<change-id> | <S/M/L 级>】
- 目标路径：spec/changes/<change-id>/
- 执行范围：阶段 <N> 至 <M>
- 受控白名单：<允许改动的目录或文件路径>
- 核心断言与红线：<特殊业务守卫或不可修改的文件>
- 交付与分支：<feature/xxx 分支，提交要求与停止条件>
```

### 4.3 紧凑回报规范

子 Agent 汇报不写假大空长篇大论，仅汇报高密度事实：
1. **拓扑与提交**：分支、Commit SHA、修改文件清单；
2. **门禁实测**：命令与当次原始 `Tests run` 关键输出（数字来自实测，不自造）；
3. **变异与证据**：变异 Label 与击红 Oracle，日志留存路径（不全量贴入聊天框）；
4. **阻塞与偏差**：未验证项或触发的停止条件。

**省钱手段**：一次只派有清晰完成判据的一片；尽量引用现有路径而不是粘贴长历史；不让多个子 Agent 在同一工作树并行写；把"查一处事实"与"实现整个阶段"分开；失败先索取最小复现和日志，再决定返修，而不是重放全仓扫描。必要的全量门禁和真实环境验证不可用局部绿灯替代。不同模型的价格或能力若未经当期确认，不在仓库文档里写死。

**测试执行分层**：开发过程（先红后绿循环、变异 verify、单类排障）定向跑相关测试类，合法且应当；**验收门禁（tasks.json 的门禁任务与复核独立复跑）必须全量双端，不得以「本案与其他测试无关」为由减面**。理由：「无关」的判断不可靠——共享 DTO、契约全量重导出、type-check 全量重编都是隐性牵连面；gate-baseline 用例计数只增不减与验收记录三要素均以全量输出为证据（出处：`AGENTS.md` 唯一门禁命令、`spec/specs/agent-harness/spec.md`「验收结论必须绑定产生它的执行」）；本仓库的历史假绿事故均由局部验证掩盖。想省时走并行化方向，不减验证面。

## 5. 审阅与升级边界

- 子 Agent 回报先当线索：看 `git status --short`、本轮 diff/提交范围、关键代码与相关验证输出；发现工作树已有用户改动或其他 Agent 改动时先区分归属，不误覆盖。阶段验收严格按 `spec/README.md` 留证，不复制数字到本文件。
- 提出问题按**影响 → 证据 → 最小修复路径 → 验收办法**呈现；只有可复现且影响当前目标的缺陷才纳入本轮返修，其余登记供用户排序，不借机扩范围。
- 需求、成本、安全、数据或迁移取舍不可替用户决定；可逆的实现细节在既定范围内给子 Agent 自主权。共享 dev 数据、真实存量库迁移及不可逆操作须先获明确授权，并区分“脚本提交”和“现场生效”。
- 每轮向用户汇报最多覆盖：**当前判断及证据、建议的下一步、需要用户裁决的唯一阻塞**；没有已核实新事实就不制造下一轮，也不自动启动子 Agent。

## 6. 新主 Agent 无缝接手与常态化协作机制

为了避免频繁切换主 Agent 会话窗口时反复制造过期交接文档与冗余上下文，主 Agent 必须遵循以下机制：

### 6.1 新主 Agent 三步接手起手式（Zero-Memory Handover）

任何新开启的主 Agent 窗口在接手项目时，**严禁要求用户手动复述背景**，必须直接依序执行三步机械自查定位现状：

1. **第一步：看物理断点（Git 事实源）**
   - 执行：`git status --short`、`git branch --show-current`、`git log -1 --oneline`。
   - 目的：核实当前分支、是否存在未提交的脏改动、最新一次提交的语义与 revision。
2. **第二步：看在途任务（变更执行事实源）**
   - 执行：检查 `spec/changes/` 下是否存在除 `archive/` 外的活动变更目录。
   - 判定：若存在在途变更，直接阅读其 `tasks.json`（哪个任务进行中、完成度与阻塞点、当前验收判据）；若无活动目录且工作树干净，说明上一变更已完全收口。
3. **第三步：看待办队列（功能规划事实源）**
   - 执行：阅读 `docs/功能待办清单.md` 与 `README.md` 的阅读路由。
   - 判定：核对当前所处的开发阶段、下一个待立案候选功能，或当前需处理的用户目标。

### 6.2 状态就地沉淀（State-in-Place）与交接红线

- **严禁新建带日期交接快照/过程日记**：严禁在 `docs/` 或仓库任意位置新建形如 `docs/指导Agent交接文档-YYYY-MM-DD.md` 或临时过程记录文件。
- **历史冗余的根源**：过去全仓产生数百个 Markdown 冗余的根本原因，正是把交接当成了“写日记”（把当时的端口、分支名、用例数、改动摘要全盘复制一份，写完即过期并制造多副本冲突）。
- **状态三处真源原则**：
  1. **代码与分支状态**：由 Git 自身管理；
  2. **在途变更与门禁证据**：就地沉淀在 `spec/changes/<change-id>/tasks.json`（任务勾选与当次命令实测 output）；
  3. **全局功能规划与决策**：就地沉淀在 `docs/功能待办清单.md` 与 `docs/需求决策记录.md`。

需了解本机历史踩坑再查 `docs/指导Agent交接文档.md` 的对应小节。环境与测试数字以现场为准，不另设一套文字副本。

### 6.3 用户新窗口唤醒模板

用户在开启全新主 Agent 会话窗口时，无需手动搬运历史对话或背景，推荐直接发送标准唤醒指令：

> “请作为指导主 Agent 接手当前项目，先执行三步起手式（git status / 在途 tasks.json / docs/功能待办清单.md），汇报当前物理断点与建议动作，不要写任何交接日记。”

## 1. 结论摘要

本轮真跑 **三个臂**（每臂 3 轮正式轮、每轮前一轮预热轮；判定一律取**臂级中位数**，见 §6）：

| 硬指标 | 原定义口径 | `default`（200 线程 / 池 20） | `tuned-t400`（400 / 20） | `tuned-t400-p100`（400 / 100） |
| --- | --- | --- | --- | --- |
| 提交 P99 < 2s | `label="POST /submit"` 逐笔，取 ≥3 轮中位数 | **2,368ms 不达标** | **6,660ms 不达标** | **2,293ms 不达标** |
| 0 丢单 | `status=2 AND answers IS NULL` = 0 | 3 轮全 0 **达标** | 3 轮全 0 **达标** | 3 轮全 0 **达标** |
| 批量落库 < 30s | `MAX(updated_time) − MAX(submit_time)`，取中位数 | 17 / 15 / 51s → 中位 **17s 达标**（单轮 51s 超标） | 49 / 51 / 60s → 中位 **51s 不达标** | 59 / 92 / 56s → 中位 **59s 不达标** |

**三条结论（都要看，只取一条会得出相反的行动）**：

1. **单改线程上限不成立，而且是负优化**（§2.4）：`tuned-t400` 的服务端均值从 460ms 涨到 1224ms，
   容量 `400 ÷ 1.224 ≈ 327 req/s` **低于**默认臂的 `200 ÷ 0.460 ≈ 435 req/s`；池 pending 峰值 169 → 357。
   ⇒ 真正的绑定约束是 **master 连接池（上限 20）**，线程上限只是它的下游。这条推翻原报告 §4.2 的归因。
2. **线程上限 + 池同步放宽才有净收益，但仍跨不过 2s**：`tuned-t400-p100` 把服务端均值压回 633ms（-48%）、
   P99 中位数从 6,660ms 回到 **2,293ms（改善 66%）**，ρ 从 ~1.5 降到 ~0.79——**改善是真的，达标是没有的**。
3. **不达标的责任已从「应用配置」转移到「宿主资源」**（§7）：p100 臂 `MySQL Threads_running` 峰值 57–103
   （默认臂 19–23）、`system_cpu_usage` 采样峰值 0.976–1.000（20 逻辑核全满）、最差连接持有 6.9–7.7s。
   ⇒ 无配置杠杆可再用，须先解决**宿主共置**（JMeter 与应用同机抢 20 核）或**降低单笔写入量**（改代码，越界）。

> **指标定义一字未改**：P99 仍是客户端逐笔、丢单仍是 DB 口径、落库时效仍是 DB 两侧端点差值
> （`loadtest/db/02-metrics.sql` 未改动）。不达标就登记不达标，**没有**把口径从 P99 换成均值或分位降级（§2.2 已论证那是降级）。
>
> **口径的精确表述**（避免自述与实现不符）：`compare-runs.py` 对 P99 取的是 `label="POST /submit"` 的**全部逐笔样本**
> （与旧报告 §3.1 一致），客户端失败的笔（1–28 笔/轮，耗时 1–17ms）**也在样本内**。
> 敏感性自证：另算「仅成功样本」的 P99，九轮差值 **+0 ~ +2ms（<0.1%）**，臂级中位数只差 ±2ms —— 口径不影响任何一条判定。
> 证据：本报告 §6 表 ① 的「全部样本 P99 / 仅成功 P99」两列。

## 2. G1：容量方案的量化裁决

### 2.1 裁决用的数字全部来自本轮真跑（不复用旧报告）

臂 `default`（不注入任何容量参数 = 框架默认）三轮实测：

| 轮次 | 客户端 P99 | 客户端均值 | **服务端均值** | 隐含并发度（占 200） | 池 pending 峰值 | Δ取连接均值 | 取连接最差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| default-r1 | 2368ms | 1837ms | **460ms** | ≥194.7（97.3%） | 169 | 267.7ms | 3708ms |
| default-r2 | 956ms | 488ms | **336ms** | ≥169.7（84.9%） | 166 | 215.8ms | 2612ms |
| default-r3 | 5834ms | 3558ms | **611ms** | ≥194.8（97.4%） | 174 | 256.1ms | 2653ms |
| **中位数** | **2368ms** | 1837ms | **460ms** | ≥194.7 | 169 | 256.1ms | 2653ms |

容量口径（沿用 `docs/submit-loadtest-report.md` §4.2，`容量 = 线程数 ÷ 服务时长`）：

```text
需求  ≈ 5000 笔 ÷ 10.0s（三轮到达跨度 10.0 / 9.9 / 9.9s）  ≈ 500 req/s
容量  = 200 ÷ 0.460s（服务端均值中位数）                    ≈ 435 req/s
ρ = 500 / 435 ≈ 1.15  > 1  ⇒ 整个突发窗口内队列持续增长（r1/r3 实测占用率 97%+）
r2 恰好相反：服务端均值 336ms ⇒ 容量 ≈ 595 req/s，ρ ≈ 0.84 < 1 ⇒ 该轮 P99 = 956ms 达标
```

**同一组配置、三轮之间服务端均值 336 → 611ms（1.82×）**，而 ρ=1 的临界点落在 400ms
（`200 ÷ T > 500 ⇒ T < 400ms`）——也就是说**不做任何改动时，系统就在饱和线上来回跨**：
跨过来的那两轮 P99 = 2368 / 5834ms，没跨过来的那轮 956ms。

### 2.2 两条路线的代价（量化对比）

| 路线 | 要满足什么 | 量化代价 | 判定 |
| --- | --- | --- | --- |
| **A. 接受「服务端均值」语义**（不动线程上限，把验收口径从客户端 P99 改为服务端均值 < 400ms） | 服务端均值必须 < 400ms | 中位数 460ms 需再降 **13%**；而实测三轮天然跨度 **336–611ms**（±33%）⇒ 必须先把服务时长方差压到 10% 以内才有把握，而**压方差没有任何现成杠杆**（§4.1 已排除 Redis 锁 / 慢 SQL / 连接池，剩下只能削减关键路径工作量 = 改代码，越界） | **不可行**：① 需要的能力不在本变更授权内；② 「接受均值语义」本身等于把对外承诺从「P99 < 2s」降级为「均值 < 400ms」，与提示词「禁止改指标定义凑数」直接冲突（§4.1 已论证它是**降级**而非等价） |
| **B. 提高线程上限** | 容量 `N ÷ T` 要显著大于 500 req/s | 取保守的 T = 460ms（本轮中位数）：`N=200 → 435 req/s（ρ=1.15，实测不达标）`、`N=300 → 652 req/s（ρ=0.77）`、`N=400 → 870 req/s（ρ=0.57）`、`N=600 → 1304 req/s（ρ=0.38）`。代价：每线程约 1MB 栈（按需提交）+ 调度开销，相对 16G/20 核可忽略；且**应用进程 CPU 实测峰值仅 0.177 核**（§5），说明交卷路径不是 CPU-bound，加线程不会先撞 CPU | **选定，N=400** |

**选定路线 B，注入 `SERVER_TOMCAT_THREADS_MAX=400`**，理由不只是「数字更大」，而是：

- N=400 在 460ms 服务时长下给 ρ=0.57，**对服务时长的漂移留了 1.83× 余量**——本轮实测的服务时长天然漂移是 1.82×，正好被这份余量覆盖；N=300（ρ=0.77）只剩 1.3× 余量，覆盖不住；
- N=400 相对 N=200 的额外资源开销在本机可忽略（栈内存 ~400MB 上限且按需提交；应用 CPU 峰值 0.177 核）；
- 未选 N=600：进一步降低 ρ 的边际收益已很小（0.57→0.38），而**同时想拿 DB 连接的线程数翻 1.5 倍**，会把 master 连接池（上限 20）压得更紧——这正是本报告的**下一个瓶颈位**（§7）。

> **读到这里请继续往下看 §2.4**：本节得出的公式 `容量 = N ÷ T` 隐含「T 与 N 无关」，该前提在复验中被**证伪**
> （T 460ms → 1224ms）。本节保留原样是为了让「假设 → 被数据推翻」这条链路可查，**不是**本报告的最终选型结论；
> 最终选型与实测容量在 §2.4 / §3.3 / §7。

### 2.4 复验对 §2.2 选型的**反证**：单改线程上限不成立（本节是被测数据推翻假设的记录）

§2.2 的容量公式 `容量 = N ÷ T` 隐含了「服务时长 T 与线程数无关」。臂 `tuned-t400` 的三轮实测**证伪了这个前提**：

| 臂 | 线程上限 | 服务端均值（中位数） | 隐含并发度 | 池 pending 峰值 | Δ取连接均值 | 取连接最差 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| default | 200 | 460ms | ≥194.7（97.3%） | 169 | 256ms | 3.7s |
| **tuned-t400** | 400 | **1224ms（+166%）** | ≥378.1（94.5%） | **357** | **598ms（+134%）** | **9.5s** |

T 从 460ms 涨到 1224ms，容量 `400 ÷ 1.224 ≈ 327 req/s` **反而低于** 200 线程时的 435 req/s。
根因由池证据直接给出：线程数翻倍后，**同时抢 20 条 DB 连接的线程数也翻倍**（pending 峰值 169 → 357），
每次取连接的平均等待从 256ms 涨到 598ms——排队点从 Tomcat 线程池**搬到了 DB 连接池**，而且排得更长。

⇒ 结论：**真正的绑定约束是 master 连接池（上限 20）**，线程上限只是它的下游。
故 §6.3 在 `tuned-t400` 之后追加一臂 `tuned-t400-p100`（线程 400 + `DB_POOL_MAX=100`），
池大小的定量依据：本轮每轮约 65000 次取连接、交卷窗口内需求约 3000 次/s，
而单次取连接占用连接的时长约 `20 ÷ (65000/105s) ≈ 32ms` ⇒ 池容量需 `3000 × 0.032 ≈ 96 ≈ 100`。

> 这一条也修正了原报告 §4.2 的结论。原报告把 P99 不达标归因于「Tomcat 线程上限 200」，
> 依据是「隐含并发度 ≥194.3 占 200 的 97%」。该观测是对的，但**把下游瓶颈当成了根因**：
> 线程被占满，恰恰因为它们都在等 DB 连接。原报告 §6.2 说「连接池未成为约束」是弱证据（只有突发后快照），
> 本轮的持续采样 + 净增量证据把这条弱结论推翻了。

### 2.3 当时为什么把线程上限作为首选杠杆（事后被 §2.4 部分推翻）

- 绑定约束的判定有实测支撑：默认臂隐含并发度 ≥194.7 且 `tomcat_threads_busy_threads` 采样峰值恒为 **200**（= 上限），说明请求确实卡在「拿不到工作线程」上（**当时这被当作根因，§2.4 证明它只是表征**）；
- 服务端均值 460ms 与客户端均值 1837ms 之差 ≈ 1377ms 就是排队时间（不在应用内计时器里），与「线程池饱和 + 近饱和排队放大」的模型自洽；
- 本轮**没有**把 JIT 效应误当容量效应：每轮正式轮前都跑了预热轮，且冷热差异被单独登记（§8.1）。

## 3. G2：注入方式与生效证明

### 3.1 注入点

`server.tomcat.threads.max` 经 Spring Boot **relaxed binding** 由环境变量 `SERVER_TOMCAT_THREADS_MAX` 注入，
**零代码改动、零配置文件改动**（`src/main/**`、`application*.yml`、`pom.xml` 全程未改）。

注入点落在 **`loadtest/start-app.sh`**（本变更新增）而不是 `docker-compose.yml`：
dev 应用跑在**宿主机**（`java -jar`），compose 只编排 MySQL/Redis/RabbitMQ/Jaeger，
把线程变量写进 compose 只会制造「改了但没生效」的错觉。故 `docker-compose.yml` 本变更**未改动**。

```bash
ARM=tuned-t400 SERVER_TOMCAT_THREADS_MAX=400 bash loadtest/start-app.sh   # 臂：调参
ARM=default bash loadtest/start-app.sh                                    # 臂：默认（不注入）
```

### 3.2 生效证明（现场输出，不是「应该生效」）

`loadtest/start-app.sh` 在实例就绪后立刻从运行期读回配置，落 `target/loadtest/app-proof-<ARM>.txt`：

```text
--- [2] /actuator/prometheus 里的 Tomcat 线程上限与水位（add-submit-observability 暴露）---
tomcat_threads_config_max_threads{name="http-nio-8080"} 400.0
tomcat_threads_current_threads{name="http-nio-8080"} 10.0
```

对照组（同一命令、不注入）：

```text
tomcat_threads_config_max_threads{name="http-nio-8080"} 200.0
```

即：**运行期读到的上限随环境变量变化**（200 → 400），且 `loadtest/summarize-samples.py`
会在整个压测窗口内断言该值恒定，避免「启动时是 400、跑着跑着变了」这种无法解释的漂移。
证据文件：`app-proof-proof400.txt`（预验证）、`app-proof-default.txt`、`app-proof-tuned-t400.txt`。

### 3.3 改后容量估算与下一个瓶颈位

**预测（注入前，按 §2.2 的公式）**：

- 改后容量 ≈ `400 ÷ 0.460s ≈ 870 req/s`，相对需求 500 req/s 有 **1.7×** 余量（ρ≈0.57）；
- **下一个瓶颈位预测：master 连接池（上限 20）及其背后的 MySQL 写入**。实测依据：`hikaricp_connections_active` 恒为 **20**（= 上限）、`hikaricp_connections_pending` 采样峰值 **166–169**、Δ取连接均值 **216–268ms**、取连接最差 **2.6–3.7s**——在 200 线程时池已经满负荷且排队；线程上限提到 400 会让「同时抢连接」的线程数翻倍。

**实测（§2.4 与 §7 回填后的真答案，预测只对了一半）**：

| 项 | 预测 | 实测 | 偏差性质 |
| --- | --- | --- | --- |
| 改后容量 | 870 req/s（ρ≈0.57） | `tuned-t400`：`400 ÷ 1.224s ≈ **327 req/s**`（**低于**默认臂 435） | **公式的前提（T 与线程数无关）被证伪** |
| 下一个瓶颈位 | master 连接池 | master 连接池 **+ MySQL 写并发 + 宿主 CPU**（§7） | 方向对，**低估了层级**：池只是第二个；第三个在宿主 |

⇒ 「改后容量」这一项**不能**按 `N ÷ T` 直接算，必须先测 T(N)。故 §6 的复验顺序是
`default` → `tuned-t400`（暴露 T 的漂移）→ `tuned-t400-p100`（把池这个下游一并打开），
再在 §7 给出**实测**的容量与新瓶颈位。**预测的 870 req/s 已被本轮数据作废，不得再被引用。**

## 4. G4：压测方法学的修订（脚本级）

原报告的「预热 / 等 TIME_WAIT / ≥3 轮取中位数」是**人工纪律**（§5、§3.3、§6 三条），
本变更把它们变成**可执行动作**，并新增两条与判定口径无关但影响可信度的修订：

| 修订 | 落地位置 | 具体动作 |
| --- | --- | --- |
| 每臂 ≥3 轮 + 每轮前预热 | 新增 `loadtest/run-arm.sh` | 一臂 N 轮（默认 3）；每轮固定顺序 **复位 → 预热轮（`WARMUP_THREADS=500`，小规模跑满一轮真实链路）→ 复位 → 正式轮**；轮间由 `run-loadtest.sh` 自动等 TIME_WAIT |
| 轮间等 TIME_WAIT 排空 | `loadtest/run-loadtest.sh` 第 2 步 | 轮前轮询 `netstat -an \| grep -c TIME_WAIT`，低于 `TIME_WAIT_MAX`（默认 1500）即放行；另有「连续 30s 不再下降且 < 3000」的基线提前退出；全过程写 `timewait-*.csv`，超时则打印声明 |
| 取中位数判定 | `loadtest/compare-runs.py` | 支持 `臂=tag1,tag2,tag3` 分组，输出**臂级中位数表**（P99 / 均值 / 服务端均值 / 并发度 / 丢单合计 / 落库尾巴 / 峰值），判定看中位数不看单轮 |

## 5. G5：连接池与线程水位的持续采样

`loadtest/run-loadtest.sh` 在压测窗口内跑**两条时间线**（取峰值，而非突发后快照）：

| 时间线 | 间隔 | 内容 | 取数方式 |
| --- | --- | --- | --- |
| `sample-<TAG>.csv`（应用侧） | 目标 0.25s（**实测周期 ~3s**，见下） | `tomcat_threads_busy/current/config_max`、`hikaricp_connections_pending/active/max`、`process_cpu_usage`、`system_cpu_usage` | 单次 `/actuator/prometheus` 抓取 + **一个** awk 解析全部 8 个指标 |
| `mq-depth-<TAG>.csv`（DB·MQ 侧） | 1s | 队列 `messages_ready/unacknowledged`、未落库计数、MySQL `Threads_connected/Running` | RabbitMQ 管理 API（退 `rabbitmqctl`）+ **一次** mysql 调用跑完 3 条 SQL |

> **采样周期的真实限制（必须声明）**：本机每次进程 spawn 实测 **~0.43s**
> （`date`×10 = 3.9s、`python -c`×10 = 5.3s、`awk`×10 = 5.4s），
> 即使把 8 个指标压成 1 次 curl + 1 次 awk，采样周期仍被顶到 **~3s**（10s 突发窗口内实测 26–28 个样本，其中落在提交突发内的约 3–5 个）。
> ⇒ **采样峰值只是下界，可能漏掉尖峰**。因此 G5 不靠采样峰值下结论，额外引入第二条**不受采样周期限制**的证据线：

> **与提示词的一处有意偏差（登记在案）**：提示词写的是「轮询 `/actuator/metrics/hikaricp.connections.pending` 等端点」，
> 实现改成了**单次抓 `/actuator/prometheus` 一次拿全 8 个指标**——`/actuator/metrics/<name>` 每指标一次 HTTP 调用，
> 在本机 spawn 开销下会把采样周期顶到 10s 以上（8 次调用 + 8 次 curl），**峰值会更容易漏尖峰**。
> 端点暴露范围（`health,info,metrics,prometheus`，来自 `add-submit-observability`）两者都覆盖，指标语义一致；取数的口径与限制如上。

**连接池累计量净增量**（`prom-before` vs `prom-after` 做差，见 §6 表 ③）：

- `hikaricp_connections_acquire_seconds_count / _sum` 的 Δ ⇒ 本轮取连接次数与平均等待；
- `hikaricp_connections_acquire_seconds_max` ⇒ 2 分钟滑窗内的**最差取连接耗时**（紧跟突发取即覆盖该轮）；
- `hikaricp_connections_usage_seconds_max` ⇒ 最差连接持有耗时；
- `hikaricp_connections_timeout_total` 的 Δ ⇒ **取连接超时（硬失败）次数**。

> 口径声明：上述 Δ 覆盖的是**整个 JMeter 窗口**（含 5000 并发登录阶段），不只是交卷突发；
> `*_max` 是 2 分钟滑窗最大值，若上一轮结束距本轮不足 2 分钟，理论上可能混入上一轮尾巴（本轮实测各轮间隔均 > 2 分钟）。

**观测覆盖的诚实边界**：`dynamic-datasource` 下 Hikari 指标**只注册了主库池**（实测 `/actuator/prometheus` 里只有 `pool="master"`），
从库池（`SLAVE_DB_POOL_MAX=10`）**不可观测**——本报告不声称「整个连接池都被观测到了」。

## 7. 新瓶颈位

### 7.1 约束在三臂之间的迁移路径（每一步都由数据推动，不是推断）

| 阶段 | 忙线程峰值 | 隐含并发度/上限 | 池 pending 峰值 | Δ取连接均值 | 服务端均值 | 落库尾巴中位 |
| --- | --- | --- | ---: | ---: | ---: | ---: |
| ① 默认（线程 200 / 池 20） | **200 = 上限**（饱和） | ≥194.7 / 200（97%） | 169 | 256ms | 460ms | 17s |
| ② 线程 400（池仍 20） | 352 | ≥378.1 / 400（95%） | **357** | **598ms（+134%）** | **1224ms（+166%）** | 51s |
| ③ 线程 400 + 池 100 | **337**（**不再饱和**） | ≥269.9 / 400（67%） | 237 | 318ms（回落） | **633ms（回落 48%）** | 59s |

**①→② 把排队点从线程池搬到了连接池**（线程池不再饱和，服务时长反而翻倍）。
**②→③ 把连接池这个下游打开后，服务时长回落一半**——这证明 ② 的恶化确实由池引起，而**不是**「线程多了就乱」。
**③ 的新问题**：线程与池都不饱和了（67% / pending 不再是恒定高水位），P99 却仍 2,293ms > 2s。⇒ 约束已离开应用。

### 7.2 ③ 的剩余约束：MySQL 写并发 + 宿主 CPU（两条独立证据）

**证据 A —— DB 侧并发与连接持有时间（`mq-depth-*.csv`、`prom-after-*.txt`）**

| 指标（采样峰值） | ① 默认 | ② 线程 400 | ③ 线程 400 + 池 100 |
| --- | ---: | ---: | ---: |
| MySQL `Threads_running` | 19 / 21 / 23 | 22 / 23 / 22 | **103 / 57 / 74** |
| MySQL `Threads_connected` | 22 | 22 | **102**（= 池上限） |
| 最差连接持有（`usage_seconds_max`） | 2.0 / 1.6 / 2.5s | 3.1 / 2.8 / 2.7s | **7.7 / 7.6 / 6.9s** |
| 交卷队列 ready 深度峰值 | 3748–4499 | 4399–4600 | **4807–4972** |
| 未落库计数峰值 | ~3600–4200 | ~4000–4200 | **~4500–4700** |

把池放大到 100 之后，MySQL 侧的 `Threads_running` 从 ~20 跳到 **57–103**：**并发的写压力被原样转嫁给了 MySQL**，
单条连接的持有时间从 2–3s 涨到 **6.9–7.7s**（同一条连接被占着 7 秒，说明 SQL 在 DB 内部排队，而不是在应用里等）。
`取连接超时` 三臂全 0 ⇒ 应用侧没有再「取不到连接」，慢是**下游慢**。

**证据 B —— 宿主 CPU（`sample-*.csv`）**

| 指标 | ① 默认 | ② 线程 400 | ③ 线程 400 + 池 100 |
| --- | ---: | ---: | ---: |
| 应用进程 CPU 峰值（占单核） | 0.177 | 0.309 | 0.434 |
| **系统 CPU 峰值**（占 20 逻辑核） | **1.000 / 0.980 / 1.000** | 0.926 / 1.000 / 1.000 | **0.990 / 0.991** |

应用自己最多只吃到 **0.43 核**（2% 的机器），而**整机 CPU 峰值反复打到 0.99–1.00**（20 核全满）。
⇒ 机器是满的，但**不是应用吃掉的**：JMeter 的 5000 线程、Docker 里的 MySQL/RabbitMQ、以及宿主上其它进程在抢同一台机器（§0：JMeter 与应用同机）。
这解释了「应用不饱和但延迟不达标」：应用在等一个**被别的进程挤占的** CPU/IO。

### 7.3 结论与可选动作（标注授权边界）

**结论**：`tune-submit-capacity` 的容量杠杆（线程上限、连接池上限）**已经被用到头**。

- 线程上限 200 → 400 单独使用是**负优化**（容量 435 → 327 req/s）；
- 线程 400 + 池 100 后容量回到 **632 req/s**（`400 ÷ 0.633s`），相对需求 500 req/s 的 ρ≈**0.79**，
  但 P99 中位数仍 **2,293ms**；
- 剩余约束**不在应用配置里**：MySQL 并发写（`Threads_running` 57–103、连接持有 6.9–7.7s）与**宿主 CPU 饱和**（0.99–1.00，其中应用仅占 0.43 核）。

**在授权内可做但本轮未做**：把 JMeter 搬离被测机（消除同机竞争）——§9 登记为「未做」。
**在授权外、须另行立项**：削减单笔写入量 / 合并 DB 往返（改代码）；`audit_log` 移出关键路径（属 G6）。

> 一句话：**「提高线程上限」这条路线本轮被完整走通并证伪为「单独无效」**；
> 把它的下游（连接池）一并打开后，收益是真实的（P99 改善 66%）但**不足以达标**，
> 而下一个约束已经跳出应用边界——**再调应用参数不会有进一步收益**。

## 8. 意外发现（与本提案假设不符或提案未预期的事实）

### 8.1 冷 JVM 的第一轮正式轮仍会被 JIT 污染——「小规模预热」不足以净化首轮

臂 `default` 第 1 轮的正式轮（P99 2368ms，服务端均值 460ms）已经**先跑过一轮 500 并发预热**，
但同一配置、同一实例的第 2 轮（P99 956ms，服务端均值 336ms）仍然明显更快——
即 500 笔的预热只能把链路「打半热」，**真正把 C2 编译推到位需要一轮满规模**。
量化：`w1`（500 笔）自身 P99 = 905ms / 客户端均值 390ms；`w2`（500 笔，此时已跑过 r1 的 5000 笔）P99 = 116ms / 均值 30ms
——**同为 500 并发预热轮，前后差 4.6 倍**。这比原报告 §5 的结论（冷/热差 68%）更严格：
**预热必须满规模，否则首轮正式轮仍应被视为「半冷」**。

### 8.2 交卷路径不是 CPU-bound，而 master 连接池（上限 20）在 200 线程时就已满负荷排队

应用进程 CPU 峰值仅 **0.177 核**（占 20 核的 0.9%），而 `hikaricp_connections_active` 恒为上限 20、
`pending` 峰值 166–169、取连接均值 216–268ms。原报告 §6.2 的结论是「池未成为约束，但属弱证据（只有突发后快照）」——
本轮的持续采样与净增量证据**改变了这个判断**：池在 200 线程下已经排队，是服务时长的重要构成项。

### 8.3 `批量落库 < 30s` 在默认臂有一轮实测 51s（原报告四轮从未超过 19s）

`default-r3` 的 `persist_tail_ms = 51000`（> 30000 阈值），同轮 `submit_window_ms = 16000`。
中位数（17s）仍达标，但**单轮超标是这个硬指标第一次被打破**，且与同轮 P99 最差（5834ms）、服务端均值最高（611ms）同轮发生
⇒ 指示同一轮的环境态（宿主 CPU/IO 竞争）同时压坏了交卷与落库两条链路。

### 8.4 轮间方差（默认臂 6.1×）大于参数效应，单轮结论一律不可信

同臂三轮 P99 的极差/最小值：`default` 2368/956/5834 → **6.1×**；`tuned-t400` 7059/6660/6107 → 1.16×；
`tuned-t400-p100` 2293/3425/1491 → 2.3×。参数效应（三臂中位数 2368 / 6660 / 2293ms）与**同臂内的方差同量级**，
G4 的「≥3 轮取中位数」因此是**下限而非充分条件**——本报告的臂级判定给的是中位数，
但同时在 §9 登记「本机 20 核共享宿主 + JMeter 同机」这一方差来源未消除。
最直接的后果：`default` 臂的中位数（2368ms）落在偏慢的一轮上，而它的最好一轮（956ms）是**唯一达标**的一轮；
**若只跑一轮，同一配置可以被判成「达标」也可以被判成「超 2.9 倍」**。

### 8.5 其它

- `w1`/`w2` 等预热轮也在 `submit-results-*.csv` 落盘，但**不参与**臂级判定（`compare-runs.py` 只统计 `*-r*`）；它们自身是「预热是否足够」的证据（§8.1）。
- 预热轮与正式轮之间存在一次 `04-reset.sql` 复位（否则预热轮的 500 笔会把答卷推到 `status=2`，正式轮压不到目标路径）；
  复位自证输出（`in_progress=5000 / submitted=0 / dedups=0 / answers_nonnull=0`）逐轮留在 `arm-<ARM>.log`。

### 8.6 调参臂新出现的 401：**客户端建连失败的次生伪影**，与容量无关（追到底了）

只有 `tuned-t400-p100` 臂三轮出现 401（28 / 22 / 9 笔），前两臂几乎为 0。逐笔追查（`loadtest/probe/diag401.py`、`diag401b.py`）后，因果链是**纯客户端**的，且每一环都有计数或时间戳证据：

| 环节 | 证据 |
| --- | --- |
| ① 登录阶段建连失败 | 21/28/7 笔 `POST /api/auth/login` 抛 `HttpHostConnectException`，**耗时 0–36ms**（根本没建上连接，不是服务端慢），且全部集中在 +8.67~8.77s 的**1 秒**内发生 |
| ② token 行数缺 | `tokens-<TAG>.csv` 行数 = 5000 − 建连失败数（4972 / 4979 / 4993）：JMX 的 `JSR223PostProcessor` **只对取到真 token 的线程落盘** |
| ③ 交卷组读越过 EOF | `CSVDataSet` 是 `recycle=false` + `stopThread=false`；交卷组 5000 个线程只有 4979 行可读 ⇒ **ramp 末端启动的最后 N 个线程取到空 token** |
| ④ 空 `Bearer` → 401 | 401 的**笔数与 ② 缺行数严格相等**（28/21/7）；时间戳全部落在交卷组起点 +10001~10021ms（**ramp 10s 结束后的 20ms 内**，即索引最大的那批线程） |

⇒ 这是**压测客户端的伪影**，不是服务端缺陷：请求没带 token，服务端返回 401 是**正确行为**。
同轮 200 笔的 P99 不受影响（401 不计入「已交卷」）；DB 侧 `status=1` 残留数与之精确对应（§6.1 自洽检查 1）。

> 归因之所以值得写下来：`tuned-t400` 臂 0–2 笔、`default` 臂 0–1 笔，而 p100 臂 9–28 笔——
> **服务端越快，登录阶段越密集地返回，客户端本地端口消耗越快**，于是越容易在建连上失败。
> 「调参臂更容易出 401」这个现象与「调参让服务端出问题」是**相反**的解释。

### 8.7 `mysql` 默认连接字符集让**复位静默假绿**（实测复现，比报错更危险）

本机 `mysql` 客户端默认 `character_set_client=gbk`（实测 `SELECT @@character_set_client` → `gbk`）。
在**未显式指定** `--default-character-set=utf8mb4` 时读 UTF-8 的 SQL 文件，行为按字面量内容分两种：

| 字面量形态 | 行为 | 是否会被发现 |
| --- | --- | --- |
| 纯中文（如 `'阶段21回归验证考'`） | `ERROR 1267 Illegal mix of collations (utf8mb4_0900_ai_ci,IMPLICIT) and (gbk_chinese_ci,COERCIBLE)`，批处理中止、退出码 1 | **会** |
| ASCII+中文混合（如 `'LOADTEST-5000-并发交卷'`） | **不报错、退出码 0**，但字面量被解成别的字符 | **不会** |

第二种的实测取证（同一文件、同一字面量，只换连接字符集）：

```text
默认 gbk ： '…' = _utf8mb4'…' → 0（不相等）   HEX(CONVERT(… USING utf8mb4)) → …2DE9AA9EE8B7BAE5BD82E6B59CE38285E5B58E
utf8mb4  ： '…' = _utf8mb4'…' → 1（相等）     HEX(CONVERT(… USING utf8mb4)) → …2DE5B9B6E58F91E4BAA4E58DB7（正确）
```

**后果（本轮真实踩到）**：`loadtest/db/03-cleanup.sql` 的 `DELETE … WHERE title='LOADTEST-5000-并发交卷'`
与它末尾的自证 `leftover_exams` **用的是同一个失真字面量**，于是「删了 0 行」与「残留 0 行」同时成立：

```text
# 不带字符集：自证打印全 0（看起来复位成功）
| leftover_users | leftover_exams | leftover_submissions |
|              0 |              0 |                    0 |
# 紧接着用带字符集的独立查询复核同一行数据：存在（id=13，title 的 HEX 与预期一致）
# 带字符集重跑同一脚本：删除 1 行，自证才真正为 0
```

**同一份隐患也罩着指标取数**：`04-reset.sql` 与 `02-metrics.sql` 都靠
`SET @exam_id = (SELECT id FROM exams WHERE title='LOADTEST-5000-并发交卷')` 推导，
漏参数会让 `@exam_id` 静默变 `NULL`，于是**所有硬指标静默变 0**——「0 丢单」会是假绿而不是真绿。
（本轮未被污染：`run-loadtest.sh`（`L105-107`、`L298`）、`run-arm.sh`（`L46`）、`prepare-data.sh`（`L43-46`）
**全部显式带了** `--default-character-set=utf8mb4`，且各自带注释说明原因；漏的是 `README.md` 里两条手工用法行。）

**本轮处置**：修订 `loadtest/README.md`（§3.1 与 §4 的手工用法行补参数 + 复位后独立复核命令；坑 #2 由「会报 `Data too long`」改写为上面两种实测行为）。
**未做**：没有改 `03-cleanup.sql` / `04-reset.sql` / `02-metrics.sql` 本体——它们属另一份变更（`add-submit-loadtest`）的资产，
且 `02-metrics.sql` 是硬指标口径本身；在脚本头部加 `SET NAMES utf8mb4` 是更彻底的修法，登记为遗留项（§9）。

### 8.8 `02-metrics.sql` 的「时钟偏差自证」项在新流程下**失去判别力**

该文件末尾的 `clock_skew_s` 注释写着「应 ≈0」，本意是「应用写入的时间戳与 DB 的 `NOW()` 对得上」。
但本轮流程是**先等队列排空再取数**（否则落库时效会被未落库计数污染），于是 `db_now − MAX(submit_time)`
必然等于「最后一笔交卷 → 取数时刻」的等待，实测 **25 / 32 / 62 / 63 / 61 / 73 / 73 / 75 / 108 秒**——
**这个数字再大也不代表时钟有偏差**，它只是等待时长。⇒ 本轮**没有**独立证明应用与 DB 的时钟一致；
替代的旁证是 DB 侧 `submit_window_ms`（12/9/16s、17/16/16s、10/13/10s）与 JMeter 侧到达跨度
（10.0/9.9/9.9s、9.9/9.8/10.3s、10.3/10.0/9.8s）在量级与顺序上吻合。补一条真正的时钟自证登记为遗留项（§9）。
